# Family Beacon — Versioning Policy

## 1. Версия проекта

Family Beacon использует **Semantic Versioning (SemVer)**:

```text
MAJOR.MINOR.PATCH
```

Текущая версия проекта хранится в корневом файле `VERSION` без префикса `v`.

Пример:

```text
0.1.0
```

В Git и пользовательских обозначениях версия записывается с префиксом `v`:

```text
v0.1.0
```

## 2. Правила изменения версии

### MAJOR

Увеличивается при несовместимом изменении архитектуры, API, модели данных или другого публичного контракта проекта.

```text
v1.4.2 → v2.0.0
```

### MINOR

Увеличивается при добавлении новой функциональности без намеренного нарушения существующей совместимости.

```text
v0.1.0 → v0.2.0
```

### PATCH

Увеличивается при исправлениях ошибок, небольших улучшениях и других изменениях, не добавляющих новую значимую функциональность.

```text
v0.2.0 → v0.2.1
```

## 3. Git tags

Для версии проекта используется Git tag:

```text
vMAJOR.MINOR.PATCH
```

Например:

```text
v0.1.0
v0.2.0
v0.2.1
```

Номер Git tag должен совпадать с версией в `VERSION`.

## 4. Baseline

Baseline — это проверенная контрольная точка проекта.

Для каждой официально зафиксированной версии baseline имеет имя:

```text
baseline-vMAJOR.MINOR.PATCH
```

Например:

```text
baseline-v0.1.0
baseline-v0.2.0
baseline-v0.2.1
```

Номер baseline всегда совпадает с номером версии проекта.

Baseline создаётся только после завершения логического этапа разработки и соответствующей проверки проекта.

## 5. Коммиты и версии

Не каждый коммит создаёт новую версию или baseline.

Обычные коммиты могут находиться между версиями:

```text
commit
commit
commit
    ↓
v0.2.0
    ↓
baseline-v0.2.0
```

Версия отражает состояние продукта, а commit — отдельное изменение в Git.

## 6. Changelog

История изменений проекта ведётся в корневом файле `CHANGELOG.md`.

Для каждой официальной версии создаётся отдельный раздел с номером версии и датой.

## 7. Baseline checklist

Перед созданием нового baseline необходимо:

1. завершить соответствующий этап разработки;
2. обновить `VERSION`;
3. обновить `CHANGELOG.md`;
4. выполнить необходимые тесты и проверки;
5. убедиться, что рабочее дерево Git чистое;
6. создать Git tag `vMAJOR.MINOR.PATCH`;
7. создать Git tag `baseline-vMAJOR.MINOR.PATCH`;
8. отправить оба tag в remote repository.

Теги не следует перезаписывать или принудительно перемещать после создания baseline.

## 8. Первый официальный baseline

Новая система версионирования Family Beacon начинается с:

```text
v0.1.0
baseline-v0.1.0
```

Версия `0.x` означает, что проект находится в активной стадии разработки и его API, архитектура и функциональность ещё могут существенно изменяться до первой стабильной версии `v1.0.0`.

## 9. Исторический baseline

До введения данной системы в проекте существовал датированный tag:

```text
baseline-2026-09-05
```

Он сохраняется как историческая точка и не переименовывается.

Новые baseline должны использовать только формат:

```text
baseline-vMAJOR.MINOR.PATCH
```
