# Family Beacon — Анализ доработок для системы обновлений

**Дата:** 05.09.2026  
**Репозиторий:** `levrangit/Family_beacon`  
**Ветка:** `develop`  
**Базовая версия проекта:** `v0.1.0`  
**Статус документа:** утверждённая проектная модель для следующего этапа реализации

---

## 1. Назначение документа

Этот документ фиксирует согласованную модель изменений **Supabase** и **Backend API**, необходимую для дальнейшей реализации системы обновлений Family Beacon.

Документ является проектным манифестом следующего этапа разработки.

Он описывает:

- окончательную модель данных для обновлений;
- ответственность Backend, Supabase и Device Agent;
- жизненный цикл обновления устройства;
- Backend API-контракт;
- правила доступа и безопасности;
- границы первого этапа реализации.

Документ **не является миграцией** и не вносит изменений в Supabase.

---

## 2. Исходная архитектура

Текущая архитектура Family Beacon сохраняется:

```text
Telegram / Telethon
        ↓
   Telegram Bot
        ↓
     Backend API
        ↓
     Supabase
        ↑
 Device Agent
```

Backend остаётся центральным API и слоем бизнес-логики.

Supabase отвечает за хранение данных, состояние, историю и метаданные.

Device Agent отвечает за фактические операции на компьютере ребёнка.

Систему обновлений не следует реализовывать как расширение существующей command queue.

---

## 3. Главный принцип модели обновлений

Система разделяется на четыре уровня:

```text
Release
   ↓
Update Policy
   ↓
Device Update
   ↓
Device Agent
```

### Release

Определяет, какая версия компонента существует и доступна для распространения.

### Update Policy

Определяет, кому, когда и какую версию разрешено устанавливать.

### Device Update

Представляет конкретную попытку обновления конкретного устройства и хранит её историю.

### Device Agent

Фактически получает пакет, проверяет его, устанавливает новую версию, перезапускается, выполняет Health Check и при необходимости сообщает о rollback.

Главный принцип:

> Supabase хранит состояние и метаданные. Backend принимает решения. Device Agent выполняет обновление.

---

## 4. Три уровня данных

Модель данных строится вокруг трёх сущностей:

```text
┌─────────────────────┐
│ Component Release   │
│ Что доступно        │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Device              │
│ Что установлено     │
│ и что назначено     │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Device Update       │
│ История попыток      │
└─────────────────────┘
```

Это позволяет не перегружать таблицу `devices` историческими данными.

Существующая таблица `devices` уже содержит основу для системы обновлений:

- `agent_version`;
- `is_online`;
- `last_seen`;
- `platform`;
- `hostname`.

Эти поля сохраняются.

Добавляются три поля:

```text

```

Итоговая логическая модель:

```text
 devices
 ├── id
 ├── child_id
 ├── device_id
 ├── name
 ├── platform
 ├── hostname
 ├── agent_version
 ├── target_agent_version
 ├── update_status
 ├── is_online
 ├── last_seen
 ├── created_at
 └── updated_at
```

## 6. Назначение полей `devices`

### `agent_version`

Фактически установленная версия Device Agent.

Пример:

```text
0.3.1
```

Это значение должно подтверждаться самим аутентифицированным Device Agent через heartbeat/operational API.

### `target_agent_version`

Версия, которую Backend назначил устройству для обновления.

Пример:

```text
0.4.0
```

Это поле управляется Backend/Update Policy, а не родительским клиентом.

### `update_status`

Текущее состояние процесса обновления.

После успешного завершения обновления устройство возвращается в нейтральное состояние `idle`, а `target_agent_version` очищается.

---

# 7. `device_update_status`

Предлагается отдельный PostgreSQL enum:

```text
idle
available
requested
downloading
verifying
installing
restarting
health_check
success
download_failed
verify_failed
install_failed
health_check_failed
rolling_back
rolled_back
```

Состояния соответствуют жизненному циклу Update Architecture.

### Нормальное состояние

```text
idle
```

означает, что обновление сейчас не выполняется.

### Доступное обновление

```text
available
```

означает, что Backend определил доступное и разрешённое обновление.

### Активное обновление

```text
requested
↓
downloading
↓
verifying
↓
installing
↓
restarting
↓
health_check
↓
success
```

### Ошибки

```text
download_failed
verify_failed
install_failed
health_check_failed
```

После ошибки может выполняться:

```text
rolling_back
↓
rolled_back
```

## 9. Назначение `device_updates`

Пример успешного обновления:

```text
component:       device-agent
from_version:    0.3.1
target_version:  0.4.0
status:          success
attempt:         1
```

Пример неудачного обновления:

```text
component:        device-agent
from_version:     0.3.1
target_version:   0.4.0
status:           rolled_back
rollback_version: 0.3.1
error_code:       HEALTH_CHECK_FAILED
```

История не удаляется при последующем успешном обновлении.

---

## 10. Почему update lifecycle не должен использовать `commands`

Существующая `commands` таблица предназначена для команд управления устройством:

```text
pending
↓
claim
↓
executing
↓
completed / failed
```

Обновление существенно сложнее:

```text
AVAILABLE
↓
REQUESTED
↓
DOWNLOADING
↓
VERIFYING
↓
INSTALLING
↓
RESTARTING
↓
HEALTH_CHECK
↓
SUCCESS
```

Оно также имеет rollback, checksum, digital signature, target version и историю попыток.

Поэтому обновление является отдельным доменом и **не должно становиться обычной командой `update_agent`**.

```text
 ├── package_signature
 ├── minimum_supported_version
 ├── release_version
 ├── is_active
 ├── published_at
 ├── created_at
 └── updated_at
```

## 12. Компонентная модель версий

Family Beacon имеет Product Version и отдельные версии компонентов.

Пример:

```text
Family Beacon v0.5.0

Backend       0.5.0
Telegram Bot  0.5.0
Frontend      0.4.2
Device Agent  0.3.1
Update        0.2.0
```

Поэтому запись Device Agent может выглядеть концептуально так:

```text
component = device-agent
version = 0.3.1
release_version = 0.5.0
```

`version` — версия самого компонента.

`release_version` — Product Release, в составе которого эта версия была опубликована.

---

# 13. Каналы обновлений

`component_releases.channel` предусматривает:

```text
stable
beta
canary
```

На первом этапе основное внимание уделяется `stable`.

Beta и Canary остаются частью архитектуры для будущего staged rollout.

---

# 14. Безопасность пакета

Для каждого пакета должны быть доступны:

```text
package_url
package_sha256
package_signature
```

Цепочка проверки:

```text
Manifest / Update decision
        ↓
package URL
        ↓
SHA-256
        ↓
digital signature
        ↓
download
        ↓
verify checksum
        ↓
verify signature
        ↓
install
```

Device Agent не должен доверять одному URL и не должен скачивать и выполнять произвольный файл без проверки.

---

# 15. `component_compatibility`

Для первой реализации предлагается отдельная, относительно простая таблица совместимости:

```text
 component_compatibility
 ├── id
 ├── component
 ├── component_version
 ├── backend_min_version
 ├── backend_max_version
 ├── status
 ├── created_at
 └── updated_at
```

Пример:

```text
device-agent | 0.3.1 | 0.4.0 | 0.5.x | supported
device-agent | 0.2.0 | 0.3.0 | 0.4.x | warning
```

Для первого этапа этого достаточно. Полноценный универсальный dependency resolver не требуется.

---

# 16. Update Policy

Update Policy является частью Backend domain logic.

Она определяет целевую версию на основании:

```text
current version
      +
channel
      +
compatibility
      +
rollout eligibility
      ↓
target version
```

На первом этапе Policy не требуется превращать в большую SQL-модель.

Позже, при реализации массового rollout, может появиться отдельная модель `update_rollouts`.

На текущем этапе её создавать не требуется.

---

# 17. Что хранится в Supabase

Supabase хранит:

- текущую версию Agent;
- назначенную целевую версию;
- текущее состояние update lifecycle;
- историю обновлений;
- сведения о доступных версиях компонентов;
- checksum;
- digital signature metadata;
- compatibility metadata.

Supabase **не является механизмом установки программного обеспечения**.

---

# 18. Что не хранится в Supabase

Не следует превращать таблицы Supabase в хранилище исполняемых файлов.

`component_releases.package_url` содержит ссылку на пакет.

Фактическое объектное хранилище пакетов пока не считается окончательно выбранным решением.

Возможное использование Supabase Storage остаётся архитектурным вариантом, но не фиксируется как обязательное решение.

---

# 19. Backend API — общая модель

API разделяется на два назначения:

```text
/devices/*
```

— пользовательское управление устройствами.

```text
/device/*
```

— operational API для Device Agent.

Существующий `/device/heartbeat` сохраняется.

---

# 20. Heartbeat

Существующий endpoint:

```text
POST /device/heartbeat
```

сохраняется и постепенно становится частью operational update channel.

Agent должен сообщать свою фактическую версию:

```json
{
  "agent_version": "0.3.1"
}
```

Backend использует это значение как подтверждение фактической установленной версии.

Ответ может содержать решение об обновлении:

```json
{
  "device": {
    "agent_version": "0.3.1"
  },
  "update": {
    "available": true,
    "target_version": "0.4.0"
  }
}
```

`available: true` не означает автоматическую немедленную установку.

Решение о назначении обновления принимает Backend/Update Policy.

---

# 21. Ownership operational state

Фактическое operational состояние устройства не должно редактироваться родительским API.

Особенно это относится к:

```text
agent_version
is_online
last_seen
update_status
```

Родитель может видеть состояние, но не должен произвольно изменять его.

`agent_version` должен подтверждаться Agent.

`is_online` и `last_seen` должны определяться Backend на основании authenticated heartbeat.

`target_agent_version` назначается Backend.

`update_status` обновляется в рамках update lifecycle.

---

# 22. Проверка доступного обновления

Предлагаемый endpoint:

```text
POST /device/update/check
```

Request:

```json
{
  "agent_version": "0.3.1"
}
```

Response:

```json
{
  "update_available": true,
  "component": "device-agent",
  "current_version": "0.3.1",
  "target_version": "0.4.0",
  "channel": "stable",
  "package": {
    "url": "...",
    "sha256": "...",
    "signature": "..."
  }
}
```

Если подходящего обновления нет:

```json
{
  "update_available": false,
  "current_version": "0.3.1"
}
```

Точные поля API должны быть реализованы с учётом существующих Pydantic-моделей Backend и обратной совместимости.

---

# 23. Начало обновления

Предлагаемый endpoint:

```text
POST /device/update/start
```

Request:

```json
{
  "target_version": "0.4.0"
}
```

Backend создаёт запись `device_updates` и переводит состояние:

```text
idle
 ↓
requested
```

При этом Backend должен повторно проверить, что указанная версия действительно разрешена для данного устройства.

Agent не должен иметь возможность самостоятельно назначить себе произвольную версию.

---

# 24. Передача статуса обновления

Предлагаемый endpoint:

```text
POST /device/update/status
```

Request:

```json
{
  "update_id": "...",
  "status": "verifying"
}
```

Другой пример:

```json
{
  "update_id": "...",
  "status": "health_check_failed",
  "error_code": "...",
  "error_message": "..."
}
```

Backend проверяет допустимость перехода состояния и обновляет `device_updates`.

---

# 25. Завершение обновления

Предлагаемый endpoint:

```text
POST /device/update/complete
```

Request:

```json
{
  "update_id": "...",
  "installed_version": "0.4.0"
}
```

Backend проверяет соответствие:

```text
installed_version == target_version
```

После успешной проверки:

```text
device_updates.status = success

devices.agent_version = 0.4.0

devices.target_agent_version = NULL

devices.update_status = idle
```

# 26. Rollback

На первом этапе отдельный публичный Agent endpoint `rollback` не требуется.

Rollback является частью lifecycle конкретного `device_updates`:

```text
health_check_failed
        ↓
rolling_back
        ↓
rolled_back
```

В истории сохраняется:

```text
rollback_version
error_code
error_message
```

Позже может появиться административная операция rollback, например в отдельном admin API.

---

# 27. Parent / Web API

Parent/Web UI может получать состояние устройства:

```text
GET /devices
GET /devices/{device_id}
```

и видеть, например:

```json
{
  "agent_version": "0.3.1",
  "target_agent_version": "0.4.0",
  "update_status": "downloading"
}
```

Также предусмотрено получение истории:

```text
GET /devices/{device_id}/updates
```

Parent не должен напрямую менять operational update state.

# 28. Права доступа

Предлагается следующая модель:

| Данные | Parent | Device Agent | Backend / Update Service |
|---|---:|---:|---:|
| `devices.name` | чтение/управление | нет | да |
| `devices.hostname` | чтение | сообщение Agent | да |
| `devices.agent_version` | чтение | подтверждение | да |
| `devices.is_online` | чтение | не напрямую | да |
| `devices.last_seen` | чтение | не напрямую | да |
| `devices.target_agent_version` | чтение | нет | да |
| `devices.update_status` | чтение | обновление lifecycle | да |
| `device_updates` своей семьи | чтение | только своего устройства | полный доступ |
| `component_releases` | нет | только через update decision | полный доступ |
| `component_compatibility` | нет | не напрямую | полный доступ |

# 29. RLS-модель

### Parent

Parent может видеть устройства и историю обновлений только своей семьи.

### Device Agent

Agent может взаимодействовать только со своим устройством.

Нельзя разрешать Agent произвольный доступ ко всем `devices` или `device_updates`.

### Backend / Update Service

Backend имеет серверный доступ для управления update lifecycle и release metadata.

Все SECURITY DEFINER/RPC-механизмы должны отдельно проверяться на необходимость повышенных прав и минимальные `EXECUTE` grants.

# 30. Audit Log и Device Update History

Эти два механизма не объединяются.

### `device_updates`

Хранит бизнес-историю обновления:

```text
что обновлялось
с какой версии
на какую
какая попытка
какой результат
был ли rollback
```

### `audit_log`

Хранит административные и security-события:

```text
кто
что
когда
```

Например, назначение rollout может быть audit-событием, а сама попытка установки — записью `device_updates`.

# 34. Что пока не реализуется

На данном этапе не следует сразу реализовывать:

- автоматическое скачивание пакетов;
- Windows updater;
- замену `FamilyBeaconAgent.exe`;
- автоматический restart Agent;
- полноценную digital-signature инфраструктуру;
- конкретное object storage;
- staged rollout;
- canary rollout;
- beta rollout;
- полноценный rollback engine;
- отдельную таблицу `update_rollouts`;
- отдельную таблицу `update_targets`;
- отдельную таблицу `update_jobs`;
- отдельную таблицу `update_tasks`;
- полноценный универсальный dependency resolver.

Эти функции остаются следующими этапами реализации Update Architecture.

# 37. Supabase Migration Workflow

Этот документ не является миграцией.

При начале реализации схема должна изменяться только через новые migration-файлы.

Правильный порядок:

```text
изменение migration-файла локально
        ↓
локальная Supabase
        ↓
локальная проверка
        ↓
тесты
        ↓
проверка diff
        ↓
PR
        ↓
только после отдельного разрешения
синхронизация с remote Supabase
```

Прямое изменение remote Supabase в обход migration workflow запрещено.

# 38. Важное ограничение на текущий момент

Проектная модель утверждена для последующей реализации, но сама система обновлений в этом документе **не считается реализованной**.

Документ фиксирует архитектурное решение, а не факт наличия соответствующих таблиц или endpoints в текущем Backend.

---

# 39. Главный архитектурный вывод

Существующая модель Family Beacon уже имеет важную основу:

```text
Device
+
Device Authentication
+
agent_version
+
Heartbeat
+
Command Queue
+
Audit Log
```

Система обновлений должна строиться поверх этой основы, но как отдельный домен.

Ключевое преобразование:

```text
agent_version + heartbeat
          ↓
Device operational state
          ↓
Device Update lifecycle
          ↓
Release metadata
          ↓
Update Policy
          ↓
Safe installation
          ↓
Health Check
          ↓
Rollback
```

Главный принцип:

> **Разработка производит Release. Update Policy решает, кому его назначить. Backend управляет lifecycle. Supabase хранит состояние и историю. Device Agent выполняет обновление и подтверждает результат.**

---

# 40. Граница ответственности компонентов

```text
GitHub
  ↓
Source + Release
  ↓
Update Service
  ↓
Update Manifest / Release metadata
  ↓
Backend
  ↓
Update Policy
  ↓
Device Agent
  ↓
Verify → Install → Health Check
  ↓
Backend
  ↓
Device Update History
  ↓
Monitoring / Administration
```

Supabase остаётся хранилищем состояния и отдельным контуром migration workflow.
