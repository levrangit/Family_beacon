# 005 — 1 этап: описание работы Device Agent

**Дата:** 2026-09-06  
**Проект:** Family Beacon  
**Компонент:** Device Agent  
**Платформа:** Windows

## 1. Цель этапа

На первом этапе фиксируется архитектура запуска и работы Device Agent на компьютере ребёнка.

Device Agent разделяется на две независимые части:

1. **Device Agent Service** — постоянная фоновая часть, работающая как Windows Service.
2. **Device Agent Tray** — пользовательская программа, работающая в пользовательской сессии Windows и отображаемая в системном трее.

Разделение необходимо для того, чтобы основной Agent продолжал работать независимо от того, вошёл ли пользователь в Windows и запущена ли пользовательская часть интерфейса.

---

## 2. Общая схема

```text
                    WINDOWS
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
  Device Agent Service        Device Agent Tray
  (Windows Service)            (User process)
          │                         │
          │                         │
          ├── Identity              ├── значок в трее
          ├── Backend               ├── статус Agent
          ├── Authentication        ├── «Регистрация»
          ├── Heartbeat             ├── настройки
          ├── Commands              ├── уведомления
          └── Policies              └── выход
                 │                   │
                 └──── IPC ──────────┘
                       │
                       ▼
                    Backend
                       │
                 ┌─────┴─────┐
                 ▼           ▼
              Telegram    Supabase
```

## 3. Device Agent Service

### 3.1. Назначение

Device Agent Service — это основная рабочая часть Agent. Он запускается как настоящий Windows Service и не содержит пользовательского интерфейса.

Service должен запускаться автоматически при старте Windows и работать независимо от входа пользователя в систему.

### 3.2. Основные обязанности

Service отвечает за:

- определение Identity компьютера;
- установление соединения с Backend;
- аутентификацию устройства;
- heartbeat;
- получение и выполнение команд;
- применение политик;
- контроль состояния Agent;
- восстановление работы после временных ошибок;
- продолжение работы при выходе пользователя из Windows.

Принцип:

> **Service = постоянно работающая фоновая часть Device Agent.**

### 3.3. Перезапуск после сбоя

Windows Service Manager должен быть настроен на автоматический перезапуск Service после аварийного завершения.

```text
Service
   ↓
 CRASH
   ↓
Windows Service Manager
   ↓
 RESTART
   ↓
Service снова работает
```

## 4. Device Agent Tray

### 4.1. Назначение

Device Agent Tray — обычная пользовательская программа, запускаемая при входе пользователя в Windows.

Она предоставляет пользователю визуальный интерфейс Agent, но не является основной рабочей частью Agent.

Принцип:

> **Tray = пользовательский интерфейс Device Agent.**

### 4.2. Технология Tray — зафиксированное решение

Для **Device Agent Tray** выбирается:

> **Python + PySide6 / Qt**

Решение принято как основное технологическое решение проекта для пользовательской части Agent.

Причины выбора:

- основной Agent уже реализуется на Python, поэтому не требуется вводить второй основной язык только ради Tray;
- PySide6 предоставляет нативную интеграцию с системным треем через `QSystemTrayIcon`;
- Qt позволяет создавать отдельные окна, меню, уведомления и настройки в едином UI-стиле;
- внешний вид можно сделать согласованным с существующим Family Beacon frontend;
- Qt поддерживает Windows и оставляет возможность расширения Agent на другие desktop-платформы в будущем;
- архитектура остаётся разделённой: Tray отвечает за UI, Service — за фоновую работу и Backend.

Windows-native технологии вроде C# + WPF/WinUI и web-based варианты вроде Tauri/Electron рассматриваются как альтернативы, но **для текущей реализации Family Beacon не выбираются**.

### 4.3. Основные функции

В системном трее пользователь должен видеть состояние Agent и иметь доступ к основным пользовательским действиям.

Предварительная структура меню:

```text
┌─────────────────────────┐
│ Family Beacon           │
│ ● Агент работает        │
├─────────────────────────┤
│ Регистрация устройства  │
│ Статус                   │
│ Настройки                │
├─────────────────────────┤
│ О программе              │
│ Выход                    │
└─────────────────────────┘
```

### 4.4. Важное правило

Закрытие Tray **не должно останавливать Device Agent Service**.

Например:

```text
Tray закрыт
    ↓
Service продолжает работать
    ↓
Heartbeat продолжается
    ↓
контроль продолжается
```

Команда **«Выход»** в Tray означает завершение пользовательского процесса Tray. Она не является командой остановки Windows Service.

## 5. Единый визуальный стиль Agent

Пользовательский интерфейс Device Agent должен использовать единый визуальный язык Family Beacon.

При этом задача состоит не в буквальном копировании web-интерфейса, а в создании нативного desktop UI в той же дизайн-системе.

### 5.1. Основные цвета

На текущем этапе фиксируются следующие базовые UI-токены:

```text
Primary       #005BBF
Primary Dark  #004493
Background    #F1F4FA
Surface       #FFFFFF
Border        #DFE3E8
Text          #181C20
Muted         #414754
```

### 5.2. Общий принцип

Окна Tray должны визуально восприниматься как часть Family Beacon:

- одинаковая логика отступов;
- близкая система скруглений;
- одинаковая визуальная иерархия;
- единый основной цвет действий;
- одинаковая логика состояний и уведомлений.

Для Windows Agent основной шрифт UI предпочтительно строить вокруг **Segoe UI**, чтобы интерфейс выглядел естественно для Windows, сохраняя визуальную близость к Family Beacon.

Системное контекстное меню самого Tray желательно оставлять максимально нативным для Windows, а основные окна Agent оформлять в едином стиле Family Beacon.

## 6. Запуск компонентов

### 6.1. Запуск Service

При включении компьютера:

```text
Windows boot
    ↓
Device Agent Service
    ↓
Identity
    ↓
Device Authentication
    ↓
Heartbeat
    ↓
Backend знает, что устройство работает
```

Service не должен зависеть от входа пользователя в Windows.

### 6.2. Запуск Tray

После входа пользователя:

```text
Windows Login
    ↓
Device Agent Tray
    ↓
Tray подключается к Service
    ↓
● Агент работает
```

Tray запускается в пользовательской сессии, поскольку ему необходимо взаимодействовать с пользователем и отображать UI.

---

## 7. Взаимодействие Tray и Service

Tray не должен напрямую обращаться к Supabase или выполнять серверную логику регистрации устройства.

Предлагаемая схема:

```text
Tray
  │
  │ IPC
  ▼
Windows Service
  │
  │ HTTPS
  ▼
Backend
  │
  ▼
Supabase
```

В качестве механизма локального IPC для Windows предварительно рассматриваются **Named Pipes**.

Преимущества такого подхода:

- не требуется открывать локальный TCP-порт;
- Service остаётся единственным компонентом, работающим с Backend;
- можно ограничить доступ к IPC;
- Tray остаётся тонким пользовательским интерфейсом.

Конкретная реализация IPC будет определена на следующем этапе разработки.

---

## 8. Запуск регистрации устройства

Регистрация запускается пользователем из Tray.

Предварительная последовательность:

```text
Tray
  ↓
«Регистрация устройства»
  ↓
Pairing Window
```

При этом UI регистрации не выполняет самостоятельно регистрацию в Supabase.

Полная последовательность взаимодействия должна быть следующей:

```text
Tray
 │
 │ registration.start
 ▼
Service
 │
 │ создаёт registration request
 ▼
Backend
 │
 │ получает временный код
 ▼
Service
 │
 │ IPC
 ▼
Pairing Window
```

После этого пользователь взаимодействует с окном регистрации.

---

## 9. Pairing Window

Pairing Window является частью пользовательского интерфейса Tray.

Окно предназначено для отображения информации, необходимой пользователю для сопряжения устройства.

ОС в этом окне **не выбирается**.

Причина: платформа определяется самим Device Agent. Пользователь не должен вручную указывать Windows/macOS/iPhone/iPad/Android.

Agent уже располагает собственной информацией об окружении, например:

```text
platform = windows
hostname = ...
windows_machine_guid = ...
os_user_sid = ...
os_username = ...
os_session_identity = ...
```

Следовательно, UI регистрации должен запрашивать только пользовательские данные, которые действительно необходимы для процесса регистрации.

### 9.1. Реализация Pairing Window

Pairing Window также реализуется на **Python + PySide6 / Qt**.

Окно не должно иметь собственной backend-логики. Оно получает данные от Tray/Service и передаёт пользовательские действия обратно в Tray.

Целевой принцип:

```text
Service
   │
   │ IPC
   ▼
Tray
   │
   ▼
PySide6 Pairing Window
```

В частности, временный pairing code должен поступать в окно от Agent, а не быть захардкожен в UI.

## 11. Поведение при выходе пользователя

Если пользователь выходит из Windows:

```text
User Logoff
    ↓
Tray завершается
    ↓
Service продолжает работать
```

Это является принципиальным требованием архитектуры.

Service должен продолжать выполнять свои фоновые функции независимо от пользовательской сессии.

---

## 12. Принципы безопасности и ответственности компонентов

### Service

Service является доверенной фоновой частью Agent и отвечает за:

- связь с Backend;
- аутентификацию устройства;
- регистрацию устройства после прохождения необходимого процесса одобрения;
- heartbeat;
- команды и политики.

### Tray

Tray отвечает за:

- пользовательский интерфейс;
- отображение состояния;
- запуск пользовательских действий;
- отображение окна регистрации;
- уведомления.

Tray не должен хранить или самостоятельно управлять долгосрочными серверными credentials устройства.

---

## 13. Принцип разделения Identity, Registration и Authentication

В архитектуре необходимо сохранять следующие различия:

```text
Identity
   ≠
Authentication

Registration Request
   ≠
Device

Pairing
   ≠
Approval

Approval
   ≠
Authentication
```

Identity описывает компьютер и среду, в которой работает Agent.

Registration Request является временным процессом начала регистрации.

Pairing связывает пользовательское действие и временный код.

Approval является отдельным решением родителя.

Authentication используется уже для доверенного взаимодействия зарегистрированного устройства с Backend.

## 15. План дальнейшей разработки

После фиксации технологии Tray дальнейшая разработка выполняется поэтапно.

### Этап A — каркас Tray

Сначала создаётся минимальный пользовательский процесс:

- Python + PySide6;
- `QApplication`;
- `QSystemTrayIcon`;
- базовое контекстное меню;
- запуск при пользовательском входе рассматривается отдельно на этапе установки Agent;
- корректное завершение только процесса Tray.

На этом этапе Service и Backend не подключаются.

### Этап B — единая UI-система Agent

Создаётся общий Qt-стиль для окон Agent на основе зафиксированных Family Beacon UI-токенов.

В него входят:

- цвета;
- шрифты;
- кнопки;
- поля ввода;
- карточки/контейнеры;
- состояния;
- отступы;
- скругления;
- уведомления.

### Этап C — PySide6 Pairing Window

Существующая концепция регистрации переносится в PySide6.

На этом этапе проверяется визуальное соответствие:

```text
Family Beacon Web UI
        │
        ▼
   общий дизайн
        ▲
        │
Device Agent Pairing Window
```

При этом не подключается реальная регистрация в Backend.

### Этап D — IPC

После проверки UI реализуется локальное взаимодействие Tray ↔ Service.

Предварительный механизм:

> **Windows Named Pipes**

Tray должен уметь запрашивать у Service состояние Agent и инициировать пользовательские действия через IPC.

### Этап E — реальный сценарий регистрации

После готовности IPC подключается реальный registration flow:

```text
Child
  ↓
Tray
  ↓
Service
  ↓
Backend
  ↓
Temporary Registration Request
  ↓
Telegram
  ↓
Parent Approval
  ↓
Service
  ↓
Device Authentication
```

Временный pairing code не является долгосрочным credential.

### Этап F — полноценный Windows Service

После UI и IPC реализуется полноценная фоновая часть:

- запуск при старте Windows;
- Identity;
- Authentication;
- Backend;
- Heartbeat;
- Commands;
- Policies;
- обработка ошибок;
- восстановление после сбоя;
- независимость от пользовательского входа и выхода.

## 16. Состояние на 2026-09-06

На текущем этапе:

- архитектура Service + Tray согласована;
- **для Device Agent Tray зафиксирован Python + PySide6 / Qt**;
- Service остаётся отдельным Windows Service на Python;
- Tray должен запускаться в пользовательской сессии;
- Tray и Service должны взаимодействовать через локальный IPC;
- предварительный механизм IPC — Windows Named Pipes;
- Pairing Window относится к пользовательской части Agent;
- Pairing Window также реализуется на Python + PySide6 / Qt;
- выбор ОС из Pairing Window удалён;
- ОС определяется самим Agent;
- backend/Supabase-логика регистрации пока не реализуется в Pairing Window;
- текущий UI-стиль должен быть согласован с Family Beacon frontend через общую визуальную систему;
- конкретный каркас PySide6 Tray ещё не создан;
- полноценный Windows Service ещё не создан;
- реальный IPC ещё не реализован;
- реальная регистрация устройства через Backend ещё не подключена.

**Следующий конкретный шаг:** создать минимальный каркас **Device Agent Tray на Python + PySide6**, затем создать/перенести Pairing Window в этот же Qt UI-стек и только после визуальной проверки переходить к IPC.
