# Регистрация устройства 0.1.1 — архитектурный анализ

Дата: 2026-09-12  
Ветка: `develop`  
Режим: read-only аудит GitHub-репозитория `levrangit/Family_beacon`

## 1. Итог

Предложенная схема регистрации физического компьютера и отдельных Windows-пользователей применима к текущей архитектуре Family Beacon.

Главное архитектурное разделение:

> **Agent принадлежит физическому компьютеру, Windows-пользователь принадлежит ребёнку, а правила могут быть собственными или унаследованными.**

То есть модель должна быть:

```text
Family
 ├── Children
 └── Devices
      └── Family Beacon Agent
           ├── Windows SID A → Вася → свои правила
           └── Windows SID B → Петя → правила Васи / свои правила
```

Сейчас проект в основном построен вокруг модели `device → child`, поэтому потребуется изменить несколько связей и протоколов.

---

## 2. Agent уже умеет определять Windows-пользователя

`agent/device_agent/identity.py` уже собирает:

- `windows_machine_guid`
- `hostname`
- `os_user_sid`
- `os_username`
- `os_session_identity`

`os_user_sid` получается через `whoami /user`.

Следовательно, базовый механизм определения Windows-пользователя уже существует. Не нужно придумывать новый способ идентификации пользователя.

Проблема только в том, что сейчас эти данные не используются как часть Backend-протокола регистрации пользователя.

---

## 3. `agent_installations` подходит для первичной установки Agent

Текущая `agent_installations` содержит:

```text
family_id
installation_code_hash
agent_secret_hash
status
device_platform
device_id
hostname
agent_version
expires_at
claimed_at
```

Установка относится прежде всего к:

```text
Family
  ↓
Physical PC
```

а не к конкретному ребёнку.

### Архитектурный вывод

В новой модели **не нужно делать `child_id` обязательной частью `agent_installations`**.

`agent_installations` должна описывать первичное подключение физического компьютера к семье.

---

## 4. `device_registration_requests` можно использовать для нового Windows-пользователя

Существующая таблица предназначена для сценария:

```text
Agent
  ↓
код
  ↓
ребёнок вводит код в Telegram
  ↓
Backend связывает регистрацию
```

Для новой модели её роль можно уточнить:

> `device_registration_requests` — регистрация нового Windows-пользователя на уже установленном физическом компьютере.

Сейчас таблице не хватает Windows identity. Для новой схемы нужны как минимум:

```text
device_id
windows_user_sid
windows_username
child_id
```

При этом сама идея временного регистрационного кода хорошо подходит для сценария «Петя хочет создать свои правила».

---

## 5. Основная проблема текущей таблицы `devices`

Сейчас `devices` содержит `child_id` и фактически предполагает:

```text
device → один child
```

Это не соответствует новой модели, потому что один физический компьютер может использоваться несколькими Windows-пользователями:

```text
PC-01
 ├── SID-A → Вася
 └── SID-B → Петя
```

Поэтому физический `device` нужно отделить от связи с ребёнком.

Логическая модель должна быть примерно такой:

```text
devices
    id
    device_id
    name
    platform
    hostname
    ...

например:

device_users
    device_id
    windows_user_sid
    windows_username
    child_id
```

То есть один физический компьютер может иметь несколько Windows-пользователей, каждый из которых связан с ребёнком.

---

## 6. `time_usage` тоже нужно отделить от `devices.child_id`

Сейчас модель предполагает, что `time_usage.child_id` должен соответствовать `devices.child_id`.

В новой архитектуре это ограничение больше не подходит.

Нужно разрешить, например:

```text
device_id = PC-01
child_id = Вася
```

и одновременно:

```text
device_id = PC-01
child_id = Петя
```

Это позволит вести раздельное использование одного физического компьютера разными детьми.

---

## 7. `time_policies` хорошо подходит для наследования правил

Сейчас политики напрямую относятся к `child_id`.

Это можно сохранить.

Не нужно копировать правила Васи в запись Пети. Лучше хранить связь, указывающую, откуда берутся эффективные правила.

Например, логически:

```text
children
    id
    name
    rules_owner_child_id
```

Пример:

```text
Вася → rules_owner_child_id = NULL
Петя → rules_owner_child_id = Вася
Маша → rules_owner_child_id = NULL
```

Тогда:

```text
Вася → свои правила
Петя → правила Васи
Маша → свои правила
```

Если Вася меняет свои правила, Петя автоматически получает изменённые правила.

### Важно

Это пока архитектурное решение. Название и конкретная структура поля могут быть изменены при проектировании миграции.

## 8. Предлагаемый сценарий первичной установки

### Шаг 1. Родитель создаёт установку для Васи

```text
Telegram
  ↓
Вася
  ↓
Создать установку
  ↓
agent_installation
```

Установка создаётся для семьи.

### Шаг 2. Установщик запускается на компьютере

Agent получает:

```text
MachineGuid = PC-01
Windows SID = SID-A
```

Вася вводит код установки.

### Шаг 3. Backend фиксирует компьютер и пользователя

Логически создаются:

```text
device
    PC-01
```

и связь:

```text
device_user
    PC-01
    SID-A
    child = Вася
```

После этого компьютер зарегистрирован, а Windows-пользователь Вася известен системе.

---

## 9. Сценарий нового пользователя Пети

Через некоторое время Петя входит под своим Windows-пользователем.

Agent отправляет Backend:

```text
device_id = PC-01
windows_user_sid = SID-B
```

Backend проверяет:

```text
PC-01 + SID-B
```

Если такой связи нет, Backend сообщает Agent, что пользователь новый.

Agent показывает Пете сообщение:

> Ты новый пользователь Family Beacon.
> Ты можешь создать свои правила пользования компьютером или пользоваться правилами Васи.

---

## 10. Петя выбирает «Использовать правила Васи»

Новый регистрационный код не нужен.

Backend просто создаёт связь:

```text
device_user
    device = PC-01
    windows_sid = SID-B
    child = Петя
```

и назначает Петю на источник правил Васи:

```text
Петя.rules_owner_child_id = Вася
```

Получается:

```text
PC-01
 ├── SID-A → Вася → свои правила
 └── SID-B → Петя → правила Васи
```

Если Вася изменит правила, Петя автоматически получает новые эффективные правила.

---

## 11. Петя выбирает «Создать свои правила»

Тогда используется регистрационный код.

```text
Agent
  ↓
создаёт device_registration_request
  ↓
генерирует код
  ↓
Петя вводит код в своей Telegram
  ↓
Backend определяет Петю
  ↓
создаёт связь Windows SID-B → Петя
  ↓
Петя получает собственные правила
```

В этом случае:

```text
Петя.rules_owner_child_id = NULL
```

и его политики хранятся отдельно.

---

## 12. Роли двух таблиц

После принятия новой модели таблицы получают чётко разделённые обязанности.

### `agent_installations`

**Первичная установка Agent на физический компьютер.**

```text
Parent
  ↓
installation code
  ↓
Windows Setup
  ↓
Agent
  ↓
Physical Device
```

### `device_registration_requests`

**Регистрация нового Windows-пользователя на уже установленном Agent**, когда пользователь хочет собственные правила.

```text
New Windows user
  ↓
registration code
  ↓
Telegram
  ↓
Child
  ↓
Device + Windows SID
```

Таким образом, обе таблицы нужны, но обслуживают разные этапы жизненного цикла.

## 13. Что уже готово в текущем проекте

У проекта уже есть существенная часть необходимого фундамента:

- Windows MachineGuid;
- Windows SID;
- Windows username;
- Agent Service;
- BackendClient;
- `agent_installations`;
- `device_registration_requests`;
- Telegram child registration;
- `children`;
- `devices`;
- `time_policies`;
- `time_usage`.

Поэтому это не требует нового архитектурного направления. Это скорее переработка существующего device/child binding и добавление Windows-user identity в Backend-протокол.

---

## 14. Что сейчас мешает реализации

Основные изменения, которые понадобятся:

1. Отделить физический `device` от ребёнка.
2. Добавить связь `device ↔ Windows user ↔ child`.
3. Передавать `windows_user_sid` из Agent в Backend.
4. Добавить Backend-протокол определения неизвестного Windows-пользователя.
5. Расширить `device_registration_requests` Windows identity.
6. Изменить ограничения `time_usage`, которые сейчас предполагают `devices.child_id`.
7. Добавить механизм источника правил для ребёнка.
8. Научить Agent показывать выбор:
   - «Создать свои правила»;
   - «Использовать правила существующего ребёнка».
9. Реализовать привязку нового Windows SID к ребёнку после Telegram-регистрации.

## 15. Итоговая архитектура 0.1.1

```text
                         FAMILY
                           │
                ┌──────────┴──────────┐
                │                     │
             CHILDREN              DEVICES
                │                     │
        ┌───────┼───────┐             │
        │       │       │             │
       Вася    Петя    Маша       PC-01
        │       │                    │
      rules    rules            Family Beacon Agent
        │       │                    │
        │       └────────┐      ┌────┴────┐
        │                │      │         │
     own rules       rules A  SID-A     SID-B
                                │         │
                               Вася      Петя
                                         │
                               own rules / rules A
```

### Главный принцип

> **Agent принадлежит физическому компьютеру. Windows-пользователь идентифицируется по SID и связывается с ребёнком. Ребёнок может иметь собственные правила либо использовать правила другого ребёнка без копирования политик.**

Эта модель поддерживает общий компьютер, несколько Windows-аккаунтов и повторное использование одного установленного Agent без повторной установки.
