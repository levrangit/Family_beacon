# Регистрация устройства агентом — анализ текущей схемы

**Дата:** 2026-09-06  
**Репозиторий:** `levrangit/Family_beacon`  
**Ветка:** `develop`  
**Статус документа:** архитектурный анализ, без изменений схемы/кода

## 1. Цель

Зафиксировать анализ текущей архитектуры Family Beacon и необходимые изменения для сценария, в котором **ребёнок инициирует регистрацию устройства через Agent UI, а завершить регистрацию может только после подтверждения родителя**.

Документ описывает целевую логику и необходимые изменения. На момент создания документа код, Supabase и существующие миграции не изменяются.

---

## 2. Авторитетный сценарий регистрации

Целевой сценарий:

```text
Agent запускается
    ↓
Ребёнок нажимает «Регистрация» в Agent UI
    ↓
Agent получает временный код / создаётся Registration Request
    ↓
Ребёнок вводит код в Telegram
    ↓
Backend идентифицирует ребёнка по Telegram ID
    ↓
Backend определяет Family через связи ребёнка
    ↓
Активному родителю/родителям отправляется запрос на подтверждение
    ↓
┌──────────────────────────────────────────────┐
│ Да → регистрация продолжается                │
│ Нет → регистрация немедленно отклоняется     │
│ Игнор → через 10 минут регистрация отклонена  │
└──────────────────────────────────────────────┘
    ↓
При «Да» атомарно создаются Device + credentials
    ↓
Agent получает возможность долгосрочной аутентификации
    ↓
Нормальная работа устройства
```

Ключевое правило:

> **Ребёнок всегда может инициировать регистрацию самостоятельно, но завершить её может только после подтверждения родителя.**

После отказа или тайм-аута Agent не останавливается и устройство остаётся незарегистрированным. Ребёнок может начать новую попытку регистрации.

---

## 3. Почему текущая схема документа 004 требует изменения

Текущий `004_регистрация_устройства_1_ этап_2026-09-05.md` описывает в основном обратное направление: родитель инициирует создание device invite, после чего Agent вводит код.

Эта модель больше не соответствует принятому сценарию.

Полезные элементы документа 004 можно сохранить:

- временный одноразовый код;
- TTL порядка 10 минут;
- Backend как источник истины;
- обязательное подтверждение родителя;
- атомарное создание Device и credentials после одобрения;
- отсутствие parent JWT на Agent.

Но сама сущность device registration должна быть перестроена вокруг **запроса на регистрацию от Agent**, а не вокруг семейного invite.

---

## 4. `devices` не должен создаваться до подтверждения

Существующая таблица `public.devices` представляет уже зарегистрированное устройство и требует как минимум:

- `child_id`;
- `device_id`;
- `name`;
- `platform`.

Поэтому создавать запись в `devices` в момент нажатия ребёнком «Регистрация» неправильно: это позволило бы неподтверждённому запросу выглядеть как уже зарегистрированное устройство.

Рекомендуемая модель:

```text
Registration Request
        ↓ parent approval
Registered Device
```

`devices` остаётся конечной сущностью зарегистрированного устройства.

---

## 5. Не следует переиспользовать `family_invites`

В Supabase уже существует механизм `family_invites`, связанный с приглашением участников/детей в семью.

Он решает другую бизнес-задачу:

```text
Family invitation
```

Регистрация устройства решает задачу:

```text
Device registration request
```

Это разные сущности с разными жизненными циклами и субъектами процесса.

Поэтому рекомендуется создать отдельную временную сущность, например:

```text
public.device_registration_requests
```

а `family_invites` оставить для семейных приглашений.

---

## 6. Предлагаемый жизненный цикл Registration Request

Логически запрос может проходить следующие состояния:

```text
CREATED
   ↓
CODE_ISSUED
   ↓
CHILD_IDENTIFIED
   ↓
WAITING_PARENT_APPROVAL
   ├── APPROVED → REGISTERED
   ├── REJECTED
   └── TIMEOUT
```

`TIMEOUT` может быть отдельным техническим terminal state, даже если в пользовательском интерфейсе это показывается как «регистрация отклонена, так как родитель не подтвердил её в течение 10 минут».

Это решение требует отдельного согласования перед реализацией.

---

## 7. Временный код

Код должен быть временным и одноразовым. Он не должен становиться долгосрочным credential устройства.

Предпочтительная модель хранения для новой сущности:

```text
code_hash
```

а не plaintext-код.

В существующей `family_invites` уже присутствует plaintext `code`, потому что он используется в семейном/родительском UI. Это не является основанием копировать такой подход в регистрацию устройства.

После истечения TTL или завершения запроса код больше не должен приниматься.

---

## 8. Идентификация ребёнка и семьи

Agent не должен самостоятельно передавать `family_id` или `child_id` как доверенные идентификаторы регистрации.

Рекомендуемая цепочка:

```text
Telegram child identity
        ↓
Backend определяет Child
        ↓
Backend определяет Family
        ↓
Backend определяет active Parent(s)
```

Таким образом, сервер остаётся источником истины для принадлежности ребёнка к семье.

---

## 9. Parent approval

После ввода кода ребёнком Backend должен определить активного родителя/родителей соответствующей семьи и отправить им запрос на подтверждение.

Необходимо явно закрепить политику для семей с несколькими активными родителями.

Рекомендуемый вариант:

> **Любой активный родитель может одобрить или отклонить запрос; первое валидное решение становится окончательным.**

Это решение должно быть подтверждено перед реализацией.

После финального решения повторные approve/reject должны быть невозможны.

---

## 10. Тайм-аут

Если родитель не отвечает в течение 10 минут:

```text
WAITING_PARENT_APPROVAL
        ↓ 10 min
TIMEOUT
```

Для пользователя это означает автоматический отказ регистрации.

После timeout:

- код недействителен;
- запрос нельзя одобрить;
- `devices` не создаётся;
- долгосрочный device token не выдаётся;
- Agent остаётся работоспособным;
- ребёнок может начать новую регистрацию.

---

## 11. Долгосрочная аутентификация устройства

В Supabase уже существуют:

- `device_auth_tokens`;
- `create_device_auth_token`;
- `authenticate_device`;
- heartbeat по device token;
- command RPCs по token.

Эту существующую систему следует использовать после успешной регистрации.

Не требуется создавать вторую независимую систему долгосрочной device authentication.

Правильная граница:

```text
Temporary registration code
        ≠
Long-term device credential
```

---

## 12. Agent identity

Текущий Agent собирает identity-факторы, включая:

- Windows MachineGuid;
- Windows user SID;
- username/session identity;
- hostname;
- platform и version.

Эти данные могут использоваться как сведения о машине/контексте регистрации.

Но:

```text
Identity ≠ Authentication
```

MachineGuid и SID не должны сами по себе считаться доказательством права устройства на доступ к backend.

Долгосрочная аутентификация после успешной регистрации должна оставаться token-based.

---

## 13. Какие backend API логически потребуются

Текущий прямой endpoint создания device не должен использоваться как основной путь нового registration flow, поскольку он не выражает состояние временного запроса и parent approval.

Концептуально потребуются отдельные операции:

### Agent

```text
Create registration request
Poll/get registration status
```

### Telegram — ребёнок

```text
Submit registration code
```

### Telegram — родитель

```text
Approve registration
Reject registration
```

После approval сервер выполняет регистрацию устройства и выдачу долгосрочного credentials.

Точные HTTP paths, payloads, RPC names и права доступа требуют отдельного проектирования.

---

## 14. Telegram Bot

По текущему состоянию Telegram Bot функциональность регистрации устройства и parent approval отсутствует как завершённый flow.

Необходимо добавить:

### Для ребёнка

- ввод временного registration code;
- понятный результат принятия кода;
- отображение состояния запроса;
- сообщение при успешной регистрации;
- сообщение при отказе;
- сообщение при timeout.

### Для родителя

- уведомление о попытке регистрации;
- информация, достаточная для принятия решения;
- кнопки `Да` / `Нет`;
- защита от повторного решения после terminal state.

---

## 15. Agent UI и Service

Текущий Agent MVP пока не содержит полноценного backend registration flow, UI pairing/registration и Windows Service.

Целевая архитектура:

```text
Windows
├── Agent Service
│     ├── automatic startup
│     ├── background
│     ├── Identity
│     ├── Backend
│     ├── Authentication
│     ├── Heartbeat
│     ├── Commands / Policies
│     └── Watchdog User UI
└── User Interface
      ├── Tray / window
      ├── Registration UI
      ├── Status
      └── Notifications
```

Agent Service должен работать автоматически и незаметно в фоне. UI является отдельным пользовательским компонентом.

Service также должен выполнять роль watchdog для UI: периодически проверять активную Windows-сессию и при неожиданном завершении UI пытаться его перезапустить, при этом сам Service продолжает работать независимо.

---

## 16. Что переиспользуется из существующей схемы

Из текущей архитектуры не нужно заново проектировать следующие части:

- `devices` как конечную сущность зарегистрированного устройства;
- `device_auth_tokens` как долгосрочные credentials;
- device authentication RPC;
- heartbeat;
- command infrastructure;
- существующие семейные связи;
- существующую идентификацию ребёнка через Telegram ID;
- существующую parent/family authorization model.

Новая логика должна в первую очередь добавить **временный registration request lifecycle** и связать его с существующими сущностями после approval.

---

## 17. Что необходимо изменить в архитектуре

### Обязательно

1. Ввести отдельную сущность `device_registration_requests` или эквивалент.
2. Разделить временный registration code и долгосрочный device credential.
3. Сделать Agent инициатором регистрации.
4. Идентифицировать ребёнка через Telegram.
5. Определять Family и Parent(s) на Backend.
6. Ввести parent approval/rejection.
7. Ввести TTL 10 минут.
8. Создавать `devices` только после approval.
9. Выдавать `device_auth_tokens` только после approval.
10. Не использовать parent JWT на Agent.
11. Не принимать `family_id`/`child_id` от Agent как доверенные значения.
12. Не использовать существующий прямой `POST /devices` как обход approval flow.

### Требует отдельного решения

1. Точная структура `device_registration_requests`.
2. Точные состояния и их названия.
3. Политика для нескольких активных родителей.
4. Формат и длина временного кода.
5. Способ генерации кода.
6. Точные REST endpoints или Supabase RPC.
7. Момент создания long-term token.
8. Состав identity metadata, сохраняемой в registration request/device.
9. Механизм обработки timeout: cron/job/backend check/DB logic.
10. Точная модель polling/notification между Agent и Backend.

---

## 18. Безопасность

Ключевые ограничения:

- временный код не является долгосрочным credential;
- код должен иметь TTL и быть одноразовым;
- нельзя доверять переданным Agent `family_id`/`child_id`;
- parent approval должен проверяться на сервере;
- после terminal state запрос нельзя изменить;
- `devices` нельзя создавать до approval;
- long-term token нельзя выдавать до approval;
- parent JWT не должен храниться/использоваться Agent;
- Agent identity не должна подменять authentication.

## 20. Вывод

Текущая схема Family Beacon уже содержит большую часть инфраструктуры, необходимой для **зарегистрированного устройства и его дальнейшей работы**. Основной архитектурный пробел находится не в `devices` или `device_auth_tokens`, а в отсутствии отдельной сущности и lifecycle для **временного запроса на регистрацию устройства**, инициированного ребёнком и ожидающего подтверждения родителя.

Поэтому правильное направление изменений:

```text
Не менять смысл существующего Device.
Не создавать второй механизм device authentication.
Не превращать family_invites в device registration.

Добавить отдельный Registration Request lifecycle.
Связать его с Child → Family → Parent.
После approval создать существующий Device + существующие credentials.
```

Это является рекомендуемой архитектурной основой для следующего этапа проектирования и реализации.
