# Анализ проекта — 2026-09-08

## Цель
Read-only анализ текущей ветки `develop`: Backend, Telegram Bot, Windows Device Agent и Supabase, чтобы определить следующий центральный компонент регистрации устройства.

## Фактическое состояние
- Windows Device Agent установлен и запускается как Windows Service `FamilyBeaconDeviceAgent`.
- Runtime запускает локальный Named Pipe `\\.\pipe\family-beacon`.
- IPC поддерживает `status`, `registration.start`, `registration.cancel`.
- Tray успешно открывает окно pairing с кодом и отмена переводит регистрацию в неактивное состояние.
- В Supabase уже есть `families`, `children`, `devices`, `device_auth_tokens`, `commands`, `family_invites` и связанные таблицы.
- Таблица `devices` пока пуста, `device_auth_tokens` также пуста.
- Telegram/Backend уже содержат части семейной и детской регистрации, но центрального persistent workflow, связывающего локальный код Windows Agent → ребёнка → подтверждение родителя → создание device → выдачу device credential, пока нет как единого контракта.

## Главный архитектурный разрыв
Сейчас локальная регистрация Agent заканчивается временным кодом. Backend и Telegram не имеют единого источника истины о жизненном цикле конкретной регистрации устройства.

## Следующий компонент
Спроектировать **Device Registration Workflow v1**:
1. persistent registration request;
2. одноразовый код и срок действия;
3. привязка к ребёнку;
4. ожидание и решение родителя;
5. создание записи `devices`;
6. выпуск и безопасная доставка device credential;
7. финальное подтверждение Agent;
8. аудит и обработка cancel/expire/failure.

## Предлагаемый принцип
Не перегружать `devices` временными состояниями. Для workflow использовать отдельную сущность `device_registration_requests`, а `devices` создавать только после родительского approve и успешной привязки.

## Следующий этап проектирования
Нужно read-only зафиксировать:
- точную схему `device_registration_requests`;
- статусы и допустимые переходы;
- роли участников;
- API-контракты Agent/Backend/Telegram;
- момент создания `devices`;
- модель выдачи и хранения `device_auth_tokens`;
- идемпотентность, TTL, отмену и аудит.

Удалённый Supabase не изменялся.
