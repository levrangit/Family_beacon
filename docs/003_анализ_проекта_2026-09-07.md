# Анализ проекта Family Beacon — 2026-09-07

## Краткое резюме

Family Beacon — система родительского контроля, построенная вокруг трёх основных частей:

1. **Backend на Python/FastAPI** — аутентификация, семьи, участники, дети, устройства, лимиты экранного времени, учёт использования времени, команды устройствам, device authentication, приглашения/регистрация ребёнка и обновления Device Agent.
2. **Device Agent** — клиент на компьютере ребёнка с собственной идентичностью устройства, pairing, IPC через named pipes, UI/tray, heartbeat, команды и механизм обновления.
3. **Supabase/PostgreSQL** — центральное хранилище, Auth, RLS, RPC, device tokens, очередь команд, heartbeat, time usage, family invites, operational state и обновления устройств.

Проект уже находится существенно дальше стадии простого прототипа. Основной фундамент архитектуры сформирован, но несколько подсистем ещё активно развиваются и требуют сведения в единую модель перед production.

## Backend

Backend организован по предметным областям. В текущем `develop` присутствуют модули для устройств, device authentication, device updates, children, families, family invites, parent registration, time usage, commands и связанных операций.

Основная доменная модель:

`profile → family → child → device`

Вокруг неё построены:

`device auth → commands → heartbeat → time usage → updates`

и отдельный поток:

`family invite → child registration`

## Device Agent

Для устройства ребёнка уже предусмотрена полноценная модель:

- уникальный `device_id`;
- привязка устройства к ребёнку;
- platform;
- hostname;
- версия агента;
- online/offline;
- `last_seen`;
- device authentication token;
- operational/update state.

В репозитории уже присутствует IPC через named pipes, а также клиентская и серверная части IPC.

В Supabase для устройств реализована модель operational/update state с состояниями, охватывающими обычное состояние, доступное обновление, установку, health check, успешное завершение и rollback.

## Supabase

Фактическая база Supabase находится на миграции `030`.

Основные таблицы:

- `profiles`
- `families`
- `family_members`
- `children`
- `devices`
- `time_policies`
- `time_usage`
- `commands`
- `audit_log`
- `device_auth_tokens`
- `family_invites`
- `device_updates`
- `component_releases`
- `component_compatibility`

Цепочка миграций охватывает initial schema, health check, device heartbeat, time usage RPC, command queue, device authentication, device command lifecycle/recovery, Telegram IDs, family invites, child registration, device operational state и device updates/release compatibility.

RLS включён на основных таблицах.

Фактических данных в базе пока мало: это соответствует стадии разработки/тестирования, а не production.

## Регистрация ребёнка

Серверная инфраструктура для регистрации ребёнка через приглашение уже существует:

- `family_invites`;
- hash приглашения;
- срок действия;
- использование/отзыв;
- `register_child_by_invite`;
- `children.telegram_id`.

Целевой пользовательский сценарий:

**ребёнок → получает код → вводит код в Telegram → родителю приходит запрос → родитель подтверждает → регистрация продолжается.**

Таким образом, основа серверной части этого сценария уже присутствует; Telegram-flow необходимо довести до полного сквозного сценария.

## Time usage

Учёт времени уже реализован в backend и Supabase. В текущем `develop` присутствует валидация обязательного `device_id` и отрицательного количества минут.

Отдельно была обнаружена ветка `fix/device-time-usage-contract`, содержащая уникальную реализацию device-authenticated time usage через `record_time_usage_for_device`. Эта функциональность на момент анализа отсутствует в текущем `develop`, поэтому ветку нельзя считать чистым мусором до отдельного архитектурного решения.

## Commands и device authentication

Supabase содержит RPC для жизненного цикла команд и device authentication:

- создание команды;
- получение/claim следующей команды;
- завершение команды;
- recovery зависших команд;
- аутентификация устройства;
- heartbeat по device token.

Это формирует достаточно зрелый серверный контур взаимодействия Device Agent с backend/database.

## Security observations

Security Advisor Supabase показывает ряд предупреждений по `SECURITY DEFINER` функциям, доступным ролям `anon` и/или `authenticated`. Среди наиболее важных RPC:

- `authenticate_device`;
- `device_heartbeat_by_token`;
- `claim_next_device_command`;
- `complete_device_command`;
- `recover_stale_device_commands`;
- `redeem_family_invite`;
- `register_child_by_invite`;
- `record_time_usage`;
- `create_family`;
- `create_family_invite`;
- `delete_parent_account`.

Сам факт наличия `SECURITY DEFINER` не означает автоматически уязвимость: некоторые функции могут быть намеренно доступны извне и самостоятельно выполнять необходимые проверки. Однако права `EXECUTE`, границы доверия и входные проверки этих RPC следует отдельно проаудировать перед production.

Отдельный конкретный сигнал: таблица `device_auth_tokens` имеет включённый RLS, но в текущей базе не имеет RLS policies. Это требует отдельной проверки.

Supabase Auth также сообщает, что защита от использования скомпрометированных паролей (leaked password protection) отключена.

## Performance observations

Supabase Performance Advisor обнаружил несколько некритичных вопросов:

- FK `commands.created_by` не имеет покрывающего индекса;
- некоторые RLS policies используют `auth.*()` таким образом, что выражение может переоцениваться для каждой строки;
- ряд индексов пока не использовался, включая индексы на `devices`, `device_updates`, `device_auth_tokens`, `family_invites`, `component_releases` и `component_compatibility`.

На текущем небольшом объёме данных это не выглядит срочной проблемой, но перед масштабированием стоит провести оптимизацию после появления реальных нагрузочных сценариев.

## Основной вывод

Проект уже имеет правильный фундамент. Главная задача текущего этапа — не создавать базовую архитектуру заново, а согласовать несколько уже существующих подсистем.

Особенно важны три направления:

1. **Telegram registration**;
2. **Device operational state / heartbeat**;
3. **Device-authenticated time usage**.

Эти направления начинают пересекаться и должны быть сведены в единую модель устройства, ребёнка, авторизации и учёта времени.

Перед дальнейшим удалением веток или крупными изменениями рекомендуется сначала определить окончательный контракт этих трёх потоков.
