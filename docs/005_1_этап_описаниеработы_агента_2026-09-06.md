# 005 — 1 этап: описание работы Device Agent

**Дата:** 2026-09-06  
**Проект:** Family Beacon  
**Компонент:** Device Agent  
**Платформа:** Windows

## 1. Цель этапа

На первом этапе фиксируется архитектура запуска и работы Device Agent на компьютере ребёнка.

Device Agent разделяется на две независимые части:

1. **Device Agent Service** — постоянная фоновая часть, работающая как Windows Service.
2. **Device Agent Tray** — пользовательская программа, работающая в пользовательской сессии Windows и отображаемая в системном трее.

Разделение необходимо для того, чтобы основной Agent продолжал работать независимо от того, вошёл ли пользователь в Windows и запущена ли пользовательская часть интерфейса.

---

## 2. Общая схема

```text
                    WINDOWS
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
  Device Agent Service        Device Agent Tray
  (Windows Service)            (User process)
          │                         │
          │                         │
          ├── Identity              ├── значок в трее
          ├── Backend               ├── статус Agent
          ├── Authentication        ├── «Регистрация»
          ├── Heartbeat             ├── настройки
          ├── Commands              ├── уведомления
          └── Policies              └── выход
                 │                   │
                 └──── IPC ──────────┘
                       │
                       ▼
                    Backend
                       │
                 ┌─────┴─────┐
                 ▼           ▼
              Telegram    Supabase
```

---

## 3. Device Agent Service

### 3.1. Назначение

Device Agent Service — это основная рабочая часть Agent. Он запускается как настоящий Windows Service и не содержит пользовательского интерфейса.

Service должен запускаться автоматически при старте Windows и работать независимо от входа пользователя в систему.

### 3.2. Основные обязанности

Service отвечает за:

- определение Identity компьютера;
- установление соединения с Backend;
- аутентификацию устройства;
- heartbeat;
- получение и выполнение команд;
- применение политик;
- контроль состояния Agent;
- восстановление работы после временных ошибок;
- продолжение работы при выходе пользователя из Windows.

Принцип:

> **Service = постоянно работающая фоновая часть Device Agent.**

### 3.3. Перезапуск после сбоя

Windows Service Manager должен быть настроен на автоматический перезапуск Service после аварийного завершения.

```text
Service
   ↓
 CRASH
   ↓
Windows Service Manager
   ↓
 RESTART
   ↓
Service снова работает
```

---

## 4. Device Agent Tray

### 4.1. Назначение

Device Agent Tray — обычная пользовательская программа, запускаемая при входе пользователя в Windows.

Она предоставляет пользователю визуальный интерфейс Agent, но не является основной рабочей частью Agent.

Принцип:

> **Tray = пользовательский интерфейс Device Agent.**

### 4.2. Основные функции

В системном трее пользователь должен видеть состояние Agent и иметь доступ к основным пользовательским действиям.

Предварительная структура меню:

```text
┌─────────────────────────┐
│ Device Agent            │
│ ● Агент работает        │
├─────────────────────────┤
│ Регистрация устройства  │
│ Статус                   │
│ Настройки                │
├─────────────────────────┤
│ О программе              │
│ Выход                    │
└─────────────────────────┘
```

### 4.3. Важное правило

Закрытие Tray **не должно останавливать Device Agent Service**.

Например:

```text
Tray закрыт
    ↓
Service продолжает работать
    ↓
Heartbeat продолжается
    ↓
контроль продолжается
```

---

## 5. Запуск компонентов

### 5.1. Запуск Service

При включении компьютера:

```text
Windows boot
    ↓
Device Agent Service
    ↓
Identity
    ↓
Device Authentication
    ↓
Heartbeat
    ↓
Backend знает, что устройство работает
```

Service не должен зависеть от входа пользователя в Windows.

### 5.2. Запуск Tray

После входа пользователя:

```text
Windows Login
    ↓
Device Agent Tray
    ↓
Tray подключается к Service
    ↓
● Агент работает
```

Tray запускается в пользовательской сессии, поскольку ему необходимо взаимодействовать с пользователем и отображать UI.

---

## 6. Взаимодействие Tray и Service

Tray не должен напрямую обращаться к Supabase или выполнять серверную логику регистрации устройства.

Предлагаемая схема:

```text
Tray
  │
  │ IPC
  ▼
Windows Service
  │
  │ HTTPS
  ▼
Backend
  │
  ▼
Supabase
```

В качестве механизма локального IPC для Windows предварительно рассматриваются **Named Pipes**.

Преимущества такого подхода:

- не требуется открывать локальный TCP-порт;
- Service остаётся единственным компонентом, работающим с Backend;
- можно ограничить доступ к IPC;
- Tray остаётся тонким пользовательским интерфейсом.

Конкретная реализация IPC будет определена на следующем этапе разработки.

---

## 7. Запуск регистрации устройства

Регистрация запускается пользователем из Tray.

Предварительная последовательность:

```text
Tray
  ↓
«Регистрация устройства»
  ↓
Pairing Window
```

При этом UI регистрации не выполняет самостоятельно регистрацию в Supabase.

Полная последовательность взаимодействия должна быть следующей:

```text
Tray
 │
 │ registration.start
 ▼
Service
 │
 │ создаёт registration request
 ▼
Backend
 │
 │ получает временный код
 ▼
Service
 │
 │ IPC
 ▼
Pairing Window
```

После этого пользователь взаимодействует с окном регистрации.

---

## 8. Pairing Window

Pairing Window является частью пользовательского интерфейса Tray.

Окно предназначено для отображения информации, необходимой пользователю для сопряжения устройства.

ОС в этом окне **не выбирается**.

Причина: платформа определяется самим Device Agent. Пользователь не должен вручную указывать Windows/macOS/iPhone/iPad/Android.

Agent уже располагает собственной информацией об окружении, например:

```text
platform = windows
hostname = ...
windows_machine_guid = ...
os_user_sid = ...
os_username = ...
os_session_identity = ...
```

Следовательно, UI регистрации должен запрашивать только пользовательские данные, которые действительно необходимы для процесса регистрации.

---

## 9. Что происходит при перезагрузке

Для уже зарегистрированного устройства:

```text
Компьютер включается
        ↓
Windows
        ↓
Device Agent Service
        ↓
Identity
        ↓
Device Authentication
        ↓
Heartbeat
        ↓
Backend знает:
«устройство работает»
```

После входа пользователя:

```text
Windows Login
       ↓
Device Agent Tray
       ↓
подключается к Service
       ↓
● Агент работает
```

Работа Service не должна зависеть от того, запущен ли Tray.

---

## 10. Поведение при выходе пользователя

Если пользователь выходит из Windows:

```text
User Logoff
    ↓
Tray завершается
    ↓
Service продолжает работать
```

Это является принципиальным требованием архитектуры.

Service должен продолжать выполнять свои фоновые функции независимо от пользовательской сессии.

---

## 11. Принципы безопасности и ответственности компонентов

### Service

Service является доверенной фоновой частью Agent и отвечает за:

- связь с Backend;
- аутентификацию устройства;
- регистрацию устройства после прохождения необходимого процесса одобрения;
- heartbeat;
- команды и политики.

### Tray

Tray отвечает за:

- пользовательский интерфейс;
- отображение состояния;
- запуск пользовательских действий;
- отображение окна регистрации;
- уведомления.

Tray не должен хранить или самостоятельно управлять долгосрочными серверными credentials устройства.

---

## 12. Принцип разделения Identity, Registration и Authentication

В архитектуре необходимо сохранять следующие различия:

```text
Identity
   ≠
Authentication

Registration Request
   ≠
Device

Pairing
   ≠
Approval

Approval
   ≠
Authentication
```

Identity описывает компьютер и среду, в которой работает Agent.

Registration Request является временным процессом начала регистрации.

Pairing связывает пользовательское действие и временный код.

Approval является отдельным решением родителя.

Authentication используется уже для доверенного взаимодействия зарегистрированного устройства с Backend.

## 14. Состояние на 2026-09-06

На текущем этапе:

- архитектура Service + Tray согласована;
- Service должен быть независимым Windows Service;
- Tray должен запускаться в пользовательской сессии;
- Tray и Service должны взаимодействовать через локальный IPC;
- Pairing Window относится к пользовательской части Agent;
- выбор ОС из Pairing Window удалён;
- ОС определяется самим Agent;
- backend/Supabase-логика регистрации пока не реализуется в Pairing Window;
- конкретная реализация Service, Tray и IPC ещё не создана.

Следующий этап разработки должен начинаться с проектирования и создания минимального каркаса **Windows Service + Tray**, после чего можно подключать пользовательские действия и реальное сопряжение устройства.
