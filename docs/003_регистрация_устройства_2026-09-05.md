# Roadmap: регистрация и подключение нового устройства ребёнка

## 1. Цель

Реализовать безопасный механизм добавления нового устройства ребёнка в Family Beacon.

Родитель должен иметь возможность открыть конкретного ребёнка в Telegram-боте и из меню этого ребёнка нажать:

**«➕ Добавить устройство»**

После этого система создаёт одноразовый код подключения. Код вводится в Family Beacon Agent на новом устройстве.

После успешного подключения:

- устройство связывается с выбранным ребёнком;
- устройство связывается с семьёй этого ребёнка;
- одноразовый код становится недействительным;
- создаются credentials для дальнейшей аутентификации устройства;
- устройство появляется в списке устройств ребёнка;
- дальнейшее взаимодействие Agent с сервером происходит через существующий механизм device authentication.

---

# 2. Основной пользовательский flow

## 2.1. Родитель открывает семью

Telegram:

```text
👨‍👩‍👧 Моя семья

├── 👦 Иван
├── 👧 Анна
└── ...
```

## 2.2. Родитель выбирает ребёнка

Например:

```text
👦 Иван

🖥 Устройства
⏱ Ограничения времени
📊 Использование
⚙️ Настройки
```

## 2.3. Родитель открывает устройства

```text
🖥 Устройства Иванa

🟢 Ivan-PC
🟢 Ivan-Laptop

➕ Добавить устройство
```

## 2.4. Родитель нажимает «Добавить устройство»

Бот создаёт device invite, связанный с конкретным ребёнком.

Например:

```text
💻 Добавление устройства

Ребёнок: Иван

Установите Family Beacon Agent
на новое устройство и запустите его.

Код подключения:

847 291

⏱ Код действителен 10 минут.

[❌ Отменить]
```

Важно:

родитель не выбирает семью или ребёнка повторно на этапе подключения.

Ребёнок уже определён контекстом меню, из которого была запущена операция.

# 3. Архитектурный принцип

Необходимо разделить два понятия:

### Pairing

Кратковременное первоначальное подключение устройства.

Используется:

```text
одноразовый код
```

### Device authentication

Постоянная аутентификация уже зарегистрированного устройства.

Используется существующий механизм:

```text
device credentials
device_auth_tokens
```

Pairing code **не должен использоваться для последующей работы Agent**.

Схема:

```text
Telegram
   │
   │ родитель выбирает ребёнка
   ▼
Child
   │
   │ "Добавить устройство"
   ▼
Device Invite
   │
   │ одноразовый код
   ▼
Family Beacon Agent
   │
   │ redeem code
   ▼
Backend / Supabase
   │
   ├── определить family_id
   ├── определить child_id
   ├── создать device
   ├── создать device credentials
   └── погасить invite
```

Новая отдельная таблица для pairing sessions не создаётся.

Используем существующую:

```text
family_invites
```

Таблица уже содержит концепцию:

- одноразового кода;
- hash кода;
- срока действия;
- отзыва;
- отметки использования;
- пользователя, создавшего приглашение.

# 5. Расширение family_invites

В `family_invites` необходимо добавить тип приглашения.

Предлагаемый enum:

```text
family_invite_type

member
device
```

Также необходимо добавить:

```text
child_id
```

Итоговая логика:

```text
invite_type = member
child_id = NULL
```

для обычного приглашения нового участника семьи.

И:

```text
invite_type = device
child_id = конкретный ребёнок
```

для подключения устройства.

---

# 6. Ограничения целостности

На уровне PostgreSQL необходимо обеспечить невозможность создания некорректных комбинаций.

Разрешено:

```text
member + NULL child_id
```

или:

```text
device + конкретный child_id
```

Запрещено:

```text
member + child_id
```

и:

```text
device + NULL child_id
```

Это должно быть защищено непосредственно базой данных, а не только Python-кодом.

```text
create_family_invite
```

необходимо сохранить для существующего сценария приглашения участника семьи.

Она должна явно создавать:

```text
invite_type = member

```

Существующее поведение приглашений членов семьи не должно быть случайно изменено.

# 8. Существующий redeem_family_invite

Существующий механизм:

```text
redeem_family_invite
```

остаётся механизмом регистрации/добавления участника семьи.

В него необходимо добавить проверку:

```text
invite_type = member
```

Таким образом, device invite нельзя будет случайно использовать через обычный member invite flow.

---

# 9. register_child_by_invite

Существующий:

```text
register_child_by_invite
```

не следует использовать для подключения устройства.

Его назначение остаётся прежним:

```text
invite
   ↓
регистрация ребёнка
```

Device pairing — отдельный сценарий:

```text
device invite
   ↓
регистрация устройства
```

Таким образом, существующий child-registration flow не смешивается с device-registration flow.

# 10. Новая RPC create_device_invite

Необходимо создать новую серверную функцию:

```text
create_device_invite
```

Назначение:

создать одноразовый код подключения устройства для конкретного ребёнка.

## Вход

Функция должна получать:

```text
child_id
```

Пользователь определяется через:

```text
auth.uid()
```

## Проверки

Функция должна проверить:

1. пользователь авторизован;
2. пользователь является родителем;
3. ребёнок существует;
4. ребёнок принадлежит семье родителя;
5. родитель имеет право управлять этим ребёнком.

Нельзя позволять родителю создать invite для ребёнка из чужой семьи.

## Создание invite

Функция создаёт:

```text
invite_type = device
child_id = выбранный ребёнок
family_id = семья ребёнка
created_by = текущий родитель
```

Код должен быть:

- криптографически случайным;
- коротким и удобным для ввода;
- одноразовым;
- храниться в БД только в виде hash.

Предлагаемый срок действия:

```text
10 минут
```

Это существенно короче стандартного member invite.

Plaintext-код возвращается родителю только во время создания приглашения.

---

# 11. Новая RPC redeem_device_invite

Необходимо создать:

```text
redeem_device_invite
```

Это основной серверный механизм первоначального подключения устройства.

## Agent передаёт

Минимально:

```text
code
device_id
platform
hostname
agent_version
```

Agent **не должен самостоятельно передавать**:

```text
family_id
child_id
```

Сервер получает их из invite.

Это принципиально важно для безопасности.

---

# 12. Алгоритм redeem_device_invite

Операция должна выполняться атомарно.

Упрощённо:

```text
code
  ↓
hash(code)
  ↓
найти family_invites
  ↓
invite_type = device?
  ↓
не expired?
  ↓
не used?
  ↓
не revoked?
  ↓
получить family_id
  ↓
получить child_id
  ↓
создать device
  ↓
создать device credentials
  ↓
пометить invite использованным
  ↓
вернуть результат Agent
```

При ошибке операция не должна оставлять частично созданное устройство.

---

# 13. Создание устройства

После успешного redeem создаётся запись в существующей таблице:

```text
devices
```

В неё должны попасть данные нового устройства, включая:

```text
child_id
device_id
platform
hostname
agent_version
```

`child_id` берётся исключительно из device invite.

Agent не определяет, к какому ребёнку относится устройство.

---

# 14. Использование существующего device authentication

Новый отдельный механизм долгосрочной аутентификации создавать не нужно.

Необходимо повторно использовать существующий:

```text
device_auth_tokens
```

и существующие функции device authentication.

После pairing:

```text
pairing code
      ↓
device credentials
      ↓
обычная device authentication
```

Pairing code после успешного использования больше не должен иметь силу.

# 15. Backend API для Telegram

Необходимо добавить endpoint, который позволит авторизованному родителю запросить device invite.

Предлагаемый endpoint:

```text
POST /children/{child_id}/device-invite
```

Backend:

1. получает текущего пользователя;
2. получает access token;
3. проверяет права родителя;
4. вызывает `create_device_invite`;
5. возвращает код и срок действия.

Telegram-бот не должен самостоятельно работать с БД.

Архитектура:

```text
Telegram Bot
     ↓
Backend API
     ↓
Supabase RPC
```

---

# 16. Backend API для Agent

Необходимо добавить endpoint для первоначального pairing.

Предлагаемый endpoint:

```text
POST /devices/pair
```

Пример запроса:

```json
{
  "code": "847291",
  "device_id": "...",
  "platform": "windows",
  "hostname": "Ivan-PC",
  "agent_version": "..."
}
```

Backend:

```text
Agent
 ↓
POST /devices/pair
 ↓
redeem_device_invite
 ↓
device + credentials
```

После успешного ответа Agent сохраняет полученные device credentials локально.

На экране с кодом должна быть кнопка:


Отдельная БД-операция отзыва invite может быть добавлена, если это потребуется архитектурой.

Если пользователь просто вышел из меню, существующий device invite автоматически истечёт через 10 минут.

# 20. Защита от повторного использования кода

Device invite должен быть:

```text
one-time
```

После успешного redeem:

```text
used_at != NULL
```

Повторное использование должно завершаться ошибкой.

Также необходимо отклонять:

```text
просроченный код
отозванный код
неверный код
member invite вместо device invite
```

# 21. Безопасность

Необходимо обеспечить следующие правила.

### 21.1. Не хранить plaintext-код

В БД:

```text
code_hash
```

а не сам код.

### 21.2. Не принимать child_id от Agent

Agent отправляет:

```text
code
```

Сервер сам определяет:

```text
child_id
family_id
```

### 21.3. Не принимать family_id от Agent

Семья определяется через invite.

### 21.4. Не использовать pairing code после регистрации

После pairing используется device authentication.

### 21.5. Проверять принадлежность ребёнка родителю

Создать invite можно только для ребёнка своей семьи.

# 23. Тесты Supabase

Необходимо добавить тесты для database/RPC flow.

Минимальный набор:

### Создание invite

- родитель создаёт invite для своего ребёнка;
- invite имеет `device` type;
- `child_id` установлен правильно;
- `family_id` соответствует семье ребёнка;
- код нельзя получить повторно из БД в plaintext.

### Авторизация

- неавторизованный пользователь не может создать invite;
- пользователь без parent permissions не может создать invite;
- родитель не может создать invite для чужого ребёнка.

### Redeem

- правильный код создаёт device;
- device привязан к правильному child;
- device привязан к правильной family;
- invite помечается использованным;
- credentials создаются.

### Ошибки

- неверный код;
- просроченный код;
- отозванный код;
- уже использованный код;
- member invite вместо device invite.

# 28. Миграции Supabase

Планируется новая migration, которая:

1. создаёт/добавляет `family_invite_type`;
2. расширяет `family_invites`;
3. добавляет `child_id`;
4. добавляет необходимые FK;
5. добавляет CHECK constraint;
6. добавляет необходимые индексы;
7. расширяет существующие RPC;
8. создаёт новые RPC:
   - `create_device_invite`
   - `redeem_device_invite`.

Точная структура migration должна быть определена после повторного аудита существующих invite/device RPC.

- утечку credentials;
- попадание pairing code в логи.

---

# 33. Критерии готовности

Функциональность считается реализованной, когда:

- родитель может открыть ребёнка;
- в меню ребёнка есть «Добавить устройство»;
- invite создаётся именно для выбранного ребёнка;
- код действует ограниченное время;
- код хранится только как hash;
- Agent может подключить устройство по коду;
- Agent не передаёт `family_id` и `child_id`;
- сервер самостоятельно определяет семью и ребёнка;
- устройство создаётся в `devices`;
- устройство связано с правильным ребёнком;
- создаются device credentials;
- invite становится одноразовым;
- повторное использование кода невозможно;
- после pairing используется существующая device authentication;
- существующий member invite flow продолжает работать;
- backend, Supabase и Agent tests проходят;
- полный end-to-end flow успешно проверен.

# 34. Ограничение изменений

До начала каждого этапа сначала проводится проверка существующей реализации.

Новые таблицы, RPC, endpoints и изменения схемы добавляются только там, где существующая функциональность не может быть безопасно переиспользована.

Никакие изменения в Family Beacon не выполняются без отдельного прямого разрешения владельца проекта.
