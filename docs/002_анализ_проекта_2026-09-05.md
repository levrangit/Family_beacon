# Анализ текущего состояния проекта Family Beacon

**Дата анализа:** 05.09.2026  
**Репозиторий:** `levrangit/Family_beacon`  
**Анализируемая ветка:** `develop`  
**Текущая версия проекта:** `v0.1.0`  

## 1. Общая оценка

Family Beacon находится на стадии **рабочего MVP / активной разработки**. Технический фундамент уже включает Backend API, PostgreSQL/Supabase, Telegram Bot, Device Agent, command queue, device authentication, family invites и систему версионирования.

Проект пока нельзя считать production-ready. Основные причины — продолжающаяся реализация Device Agent и контроля времени, развитие Web UI, расширение интеграционных тестов и необходимость отдельного security hardening Supabase.

## 2. Правила проекта

Перед подготовкой анализа был прочитан обязательный файл `правила проекта для разработки.md`.

Ключевые правила: изменения только с прямого разрешения пользователя; migration-файлы являются источником истины схемы; удалённую Supabase нельзя изменять прямым SQL в обход migration workflow; SQLite не используется; секреты, токены, JWT и `.env` нельзя выводить; после изменений требуются проверки.

В рамках подготовки данного документа удалённая Supabase **не изменялась**.

## 3. Архитектура

```text
Telegram / Telethon
        ↓
   Telegram Bot
        ↓
     Backend API
        ↓
     Supabase
        ↑
 Device Agent
```

Telegram Bot отвечает за пользовательский интерфейс, Backend — за центральную бизнес-логику и API, Supabase — за данные, Device Agent — за операции непосредственно на компьютере ребёнка, Frontend — за web-интерфейс управления.

**Вывод:** основную архитектуру переписывать не требуется; задача — довести существующие компоненты до согласованного production-поведения.

## 4. GitHub и версионирование

Текущая версия — **`v0.1.0`**. Корневой `VERSION` содержит `0.1.0`.

Версионирование основано на Semantic Versioning. Используются `v0.1.0` и `baseline-v0.1.0`.

Версия Telegram отображается без префикса `v`:

```text
🌟 Семейный маяк · 0.1.0
```

Версия в Telegram должна браться из единого источника `VERSION`, а не быть захардкожена в отдельных файлах.

## 5. Telegram Bot

Telegram-интеграция построена на Telethon/MTProto. Основной `bot.py` использует `BackendClient`; прямой доступ Telegram Bot к Supabase не используется.

### Родительское меню

```text
🌟 Семейный маяк · 0.1.0

🏠 Семья
👤 Профиль
👶 Дети
📨 Приглашения
🗑 Забыть меня
```

### Детское меню

```text
🌟 Семейный маяк · 0.1.0

Привет, <имя>!

👤 Профиль
⏱ Время
💻 Устройства
```

Названия кнопок нейтральные: без слов «Мой», «Мое», «Мои».

Родительский flow включает `/start`, регистрацию, профиль, семью, детей, приглашения и удаление аккаунта. Детский flow включает регистрацию через invite, профиль, время и устройства.

В последней локальной проверке Telegram-набора после восстановления обработчика регистрации и динамических version assertions было **46 passed**.

## 6. Регистрация и Family Invites

Родитель регистрируется через Telegram → логин → пароль → Backend → Supabase Auth → профиль.

Для ребёнка используется схема:

```text
Родитель
   ↓
создание invite
   ↓
код
   ↓
Ребёнок
   ↓
код + имя
   ↓
Backend
   ↓
children
   ↓
Child Menu
```

В `family_invites` поддерживаются состояния `active`, `used`, `expired`, `revoked`.

В модели присутствуют `code_hash` и открытый `code`: hash используется для проверки, открытый код — для отображения родителю. Перед production следует отдельно оценить необходимость хранения открытого кода.

## 7. Backend

Backend является центральным API layer на FastAPI. Он обслуживает authentication, families, children, devices, time policies, time usage, commands, Telegram operations, device heartbeat/authentication, command queue и invites.

Использование Backend как единой точки бизнес-логики является правильным архитектурным решением.

## 8. Supabase / PostgreSQL

Удалённая база работает на PostgreSQL 17.

Основные таблицы:

- `profiles`;
- `families`;
- `family_members`;
- `children`;
- `devices`;
- `time_policies`;
- `time_usage`;
- `commands`;
- `audit_log`;
- `family_invites`;
- `device_auth_tokens`.

Схема поддерживает пользователей и роли, семьи, детей, устройства, политики времени, учёт времени, команды устройств, аудит, приглашения, device authentication, heartbeat, recovery и удаление родительского аккаунта.

Схема развивается через migration-файлы. Migration workflow должен оставаться единственным способом изменения схемы.

## 9. Device Agent и command queue

Система команд построена вокруг `commands` и жизненного цикла:

```text
Backend → command → pending → claim → Device Agent → execute → complete / failed
```

Предусмотрены команды `get_status`, `lock`, `unlock`, `shutdown`, `restart`, `sleep`, `get_device_state`, `set_time_limit`, `block_app`, `unblock_app`.

Device authentication и device tokens отделены от пользовательской авторизации.

Фундамент уже существует, но реальный контроль времени, системный мониторинг, Windows Service, auto-update, recovery и расширенное управление приложениями ещё требуют развития.

## 10. Heartbeat и мониторинг

Схема предусматривает `is_online`, `last_seen`, hostname, platform и agent version. Есть отдельный heartbeat/device authentication механизм.

Следующий уровень зрелости — сделать heartbeat полноценным operational-механизмом для достоверного определения состояния устройства.

## 11. Time Control

В Supabase предусмотрены `time_policies` и `time_usage`. Telegram уже умеет показывать использованное время, дневной лимит, оставшееся время и отсутствие лимита.

Однако отображение данных и фактическое enforcement — разные задачи. Production-цикл должен выглядеть так:

```text
Policy → Usage collection → Limit calculation → Agent enforcement → Block / allow → Actual usage
```

## 12. Frontend

Frontend находится на более ранней стадии, чем Backend и Telegram Bot. Часть интерфейса является будущей web-консолью и требует перехода от локального/mock state к реальным backend operations.

Целевой поток:

```text
Frontend → Backend API → Supabase → Device Agent
```

Frontend пока не следует считать завершённым production-интерфейсом.

## 13. CI/CD и тестирование

В проекте присутствуют GitHub Actions для основных направлений проверки, включая backend, Supabase и SonarQube.

Тестовая база включает Backend, Telegram Bot, Device Agent, invite flow, registration flow, меню и handlers.

Следующий уровень — интеграционные и E2E проверки полного жизненного цикла Telegram → Backend → Supabase → Device Agent.

## 14. Supabase Security

Это одна из главных зон технического долга.

Security Advisor указывает на предупреждения, связанные с публичным выполнением `SECURITY DEFINER` функций и их правами `EXECUTE`.

Особое внимание требуется функциям device authentication, command queue, heartbeat, family invites, child registration и удаления аккаунта.

Правильное направление hardening:

```text
SECURITY DEFINER
        ↓
проверка необходимости повышенных прав
        ↓
анализ EXECUTE grants
        ↓
REVOKE лишних прав
        ↓
GRANT только необходимым ролям
        ↓
локальная проверка
        ↓
migration
```

Нельзя просто удалить `SECURITY DEFINER`: часть функций действительно может требовать повышенных прав.

Также перед production рекомендуется включить **Leaked Password Protection** в Supabase Auth.

## 15. Supabase Performance

Критических проблем производительности текущего масштаба не выявлено.

Advisor указывает, среди прочего, на foreign key без отдельного индекса для `commands.created_by`, возможность оптимизации некоторых RLS policies с `auth.uid()` и несколько пока неиспользуемых индексов.

Неиспользуемые индексы пока не следует удалять автоматически: проект активно развивается.

## 16. Edge Functions

Удалённый проект сейчас не использует Supabase Edge Functions. Это не является проблемой: текущая архитектура с центральным Backend API остаётся логичной.

## 17. Production readiness

Family Beacon пока не готов к полноценному production release.

Основные причины:

1. Device Agent ещё развивается;
2. enforcement ограничения времени требует доведения до полноценного системного поведения;
3. frontend требует дальнейшей интеграции с backend;
4. Supabase требует security hardening;
5. требуется расширение integration/E2E тестирования;
6. release/update/rollback контур ещё не доведён до окончательного production-процесса.

## 18. Приоритет дальнейшей разработки

### Этап 1 — стабилизация `develop`

- завершать текущие изменения Telegram Bot;
- проверять CI;
- поддерживать полностью зелёные тесты;
- не допускать регрессий регистрации.

### Этап 2 — Child / Family integration

- проверка invite lifecycle;
- проверка семейных связей;
- проверка прав родителя и ребёнка;
- расширение integration tests.

### Этап 3 — Supabase security hardening

- инвентаризация `SECURITY DEFINER`;
- проверка `EXECUTE` grants;
- проверка RLS;
- проверка `anon` / `authenticated` доступа;
- включение необходимых Auth security controls.

### Этап 4 — Device Agent

- heartbeat;
- system information;
- device state;
- реальное управление временем;
- блокировка приложений;
- Windows Service;
- recovery;
- auto-update.

### Этап 5 — Frontend

Перевести UI от прототипной модели к полноценной работе через Backend API.

### Этап 6 — Release / Update Service

После стабилизации основных компонентов реализовать release, distribution, health check, update и rollback.

## 19. Когда обновлять `main`

`main` не должен обновляться после каждого небольшого изменения.

Рабочая модель:

```text
feature/fix branch
        ↓
       PR
        ↓
     develop
        ↓
 тесты + CI + проверка
        ↓
 стабильная контрольная точка
        ↓
       PR → main
        ↓
 release tag / baseline
```

`develop` — основная ветка активной разработки, `main` — стабильная ветка. `main` следует обновлять только после того, как очередной набор изменений в `develop` станет проверенной стабильной версией.

## 20. Что не следует менять без отдельного решения

- основную архитектуру без необходимости;
- бизнес-логику Backend переносом непосредственно в Telegram Bot;
- PostgreSQL/Supabase на SQLite;
- remote Supabase прямым SQL;
- `SECURITY DEFINER` функции без анализа;
- индексы только потому, что Advisor сейчас считает их неиспользуемыми;
- `main` после каждого небольшого изменения.

## 21. Итоговый вывод

Family Beacon уже вышел за пределы простого прототипа. В проекте существует связанный фундамент:

```text
Auth
 ↓
Family
 ↓
Child
 ↓
Invite
 ↓
Device
 ↓
Command
 ↓
Device Agent
```

Telegram Bot предоставляет рабочие пользовательские сценарии, Backend выступает центральным API, а Supabase содержит необходимые сущности и механизмы для дальнейшего развития.

Главная задача следующего этапа — **не расширять проект хаотично, а последовательно довести существующую цепочку до production-уровня**.

Приоритеты:

1. стабильность `develop`;
2. интеграционные проверки;
3. Supabase security hardening;
4. Device Agent и time enforcement;
5. полноценный Frontend;
6. release/update/rollback.
