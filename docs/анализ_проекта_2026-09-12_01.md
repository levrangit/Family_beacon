# Анализ проекта Family Beacon — 2026-09-12

## 1. Общая архитектура

Family Beacon уже сформирован как распределённая система Family Link-подобного типа:

```text
                         ┌──────────────────┐
                         │     Frontend     │
                         │ React / Vite / TS│
                         └────────┬─────────┘
                                  │
                                  ▼
┌───────────────┐        ┌──────────────────┐
│ Telegram Bot  │───────►│     Backend      │
│   Telethon    │ HTTP   │ FastAPI / Python │
│ + Whisper     │        └────────┬─────────┘
└───────────────┘                 │
                                  │
                         ┌────────▼─────────┐
                         │     Supabase     │
                         │ PostgreSQL + RLS │
                         └────────┬─────────┘
                                  │
                         ┌────────▼─────────┐
                         │ Device Agent     │
                         │ Windows/...      │
                         └──────────────────┘
```

Основные подсистемы:

- React/Vite frontend;
- FastAPI backend;
- Telegram bot на Telethon;
- Whisper для голосовых сообщений;
- Device Agent;
- Supabase/PostgreSQL;
- RLS и RPC;
- команды устройствам;
- регистрация устройств;
- установка агента;
- backend/frontend/agent/Telegram tests;
- GitHub Actions и SonarQube.

## 2. Главное состояние проекта

Архитектура в целом сформирована хорошо. Главный текущий риск — не структура проекта, а рассинхронизация контрактов между компонентами.

Компоненты развиваются с разной скоростью, поэтому уже обнаружены ситуации вида:

```text
BackendClient ──────► endpoint отсутствует
Service ────────────► endpoint есть в логике
Bot handler ────────► функция требует новый argument
Bot ────────────────► backend URL недоступен
Agent ──────────────► старый endpoint
```

Следующий этап проекта должен быть направлен прежде всего на синхронизацию существующих API-контрактов, а не на добавление новых функций.

Архитектура Telegram-бота разумно разделена по функциональности.

В `start.py` используются состояния регистрации:

Меню семьи уже содержит кнопку профиля.

### FakeTLS MTProto

Подключение Telegram через FakeTLS MTProxy исправлено через `tgnet` и `TgNetConnectionTls`.

Фактический запуск ранее показал:

```text
[TELEGRAM] MTProto FakeTLS proxy configured
[TELEGRAM] Connected
[BOT] Family Beacon Telegram bot started
```

Следовательно, транспорт Telegram сейчас не является проблемой.

### Ошибка registration_sessions

В `bot.py` остаются три вызова `handle_device_registration_message/action`, которым не передаётся `registration_sessions`, хотя соответствующие функции уже требуют третий аргумент.

Требуемые вызовы:

```python
await handle_device_registration_message(
    adapted_event,
    backend,
    registration_sessions,
)
```

```python
await handle_device_registration_message(
    event,
    backend,
    registration_sessions,
)
```

```python
await handle_device_registration_action(
    event,
    backend,
    registration_sessions,
)
```

Это локальный runtime/refactor bug, а не архитектурная проблема.

## 5. Обнаруженные API contract bugs

### Child dashboard

`telegram_bot/backend_client.py` обращается к:

```text
GET /telegram/child/{telegram_id}/dashboard
```

При этом `TelegramChildService` содержит реализацию dashboard, но соответствующий FastAPI route в текущем `main.py` не обнаружен.

Итого:

```text
Service       ✅
Client        ✅
FastAPI route ❌
```

Это необходимо исправить.

### Device Registration

Backend-модуль `device_registration.py` уже содержит:

```text
create_device_registration_request()
submit_device_registration_code()
get_device_registration_request()
cancel_device_registration_request()
```

Но в FastAPI опубликованы только:

```text
POST /device-registration/requests
POST /device-registration/submit-code
```

При этом Device Agent ожидает:

```text
POST /device-registration/requests
GET  /device-registration/requests/{request_id}
POST /device-registration/cancel
```

То есть два endpoint отсутствуют на HTTP-уровне, хотя бизнес-логика для них уже существует.

## 6. Supabase

Основная схема содержит:

```text
profiles
families
family_members
children
devices
time_policies
time_usage
commands
audit_log
```

Также используются enums:

```text
member_type
device_platform
command_status
command_type
```

В миграциях реализованы:

- foreign keys;
- индексы;
- updated_at triggers;
- helper functions;
- RLS;
- grants;
- автоматическое создание profile после Supabase Auth;
- atomic `create_family()`;
- проверка соответствия `time_usage.child_id` и `devices.child_id`;
- RPC для heartbeat;
- RPC для usage;
- command queue;
- device authentication;
- claim/complete device commands.

SQLite в архитектуре не используется.

### RLS

Концепция RLS хорошая:

- пользователь видит собственный профиль;
- пользователь не может самостоятельно менять `role`, `is_active`, `telegram_id`;
- семейные данные ограничены членством в семье;
- операции родителей ограничены `is_family_parent()`;
- device/time policy/usage/commands связаны с семьёй через устройство или ребёнка.

Это хороший фундамент безопасности.

## 12. Рекомендуемый следующий этап

Не добавлять новые функции до завершения API Contract Audit.

Для каждого клиента составить таблицу:

```text
Client
  ↓
HTTP method
  ↓
Endpoint
  ↓
Request schema
  ↓
Response schema
  ↓
Authentication
  ↓
Backend implementation
  ↓
Test
```

Проверить таким образом:

1. Telegram Bot ↔ Backend;
2. Device Agent ↔ Backend;
3. Frontend ↔ Backend;
4. Backend ↔ Supabase RPC/schema.

После этого пройти ключевой E2E сценарий регистрации устройства.
