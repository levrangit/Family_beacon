# Family Beacon — Правила проекта для разработки

Этот файл содержит обязательные правила работы с проектом Family Beacon.

## 1. Изменения проекта

- Ничего не изменять в проекте без прямого разрешения пользователя.
- Перед любым изменением сначала прочитать этот файл и учитывать все действующие правила.

## 2. Supabase migrations — строгое правило

- **Никогда не применять миграции напрямую к удалённой (remote) Supabase базе.**
- Сначала создать или изменить migration-файл **локально в Git**.
- Сначала применить миграцию к **локальной Supabase**.
- Локально проверить, что миграция успешно применяется и результат корректен.
- Только после успешной локальной проверки синхронизировать/применять миграцию к remote Supabase **штатным способом из консоли/CLI**.
- Не выполнять прямые изменения схемы remote Supabase в обход migration workflow.
- Если migration history remote отличается от локальной, сначала анализировать и исправлять историю безопасным способом; не выполнять SQL миграцию повторно только ради исправления истории.

## 3. Источник истины для схемы

- Migration-файлы в `supabase/migrations/` являются источником истины для схемы Supabase.
- Новое изменение схемы оформлять новой миграцией, а не редактировать уже применённую миграцию без явной необходимости и разрешения.

## 4. Безопасность

- Не выводить и не публиковать секреты, токены, пароли, JWT или содержимое `.env`.
- Service-role ключ Supabase использовать только на backend и не передавать клиенту Telegram/frontend.

## 5. SQLite

- **SQLite в проекте Family Beacon не используется.**

## 6. Проверки

- После изменения файлов обязательно выполнять соответствующую проверку/тест.
- В инструкциях для Codespaces, если команда создаёт или изменяет файл, по возможности выполнять проверку результата в той же команде.
