# Этап 1 — регистрация устройства агентом: изменения Telegram-бота

**Дата:** 2026-09-06  
**Репозиторий:** `levrangit/Family_beacon`  
**Ветка:** `develop`  
**Статус:** read-only архитектурный анализ, без изменений реализации

## 1. Цель этапа

Определить, что необходимо изменить в Telegram-боте для перехода на новую схему регистрации устройства, в которой:

> **Ребёнок инициирует регистрацию на Agent, вводит временный код в Telegram, а завершить регистрацию можно только после подтверждения родителя.**

Этот документ фиксирует первый этап реализации. Код, Supabase и существующая Telegram-логика во время анализа не изменялись.

---

## 2. Новая модель

```text
Windows Agent
    ↓
Registration Request
    ↓
временный код
    ↓
Telegram ребёнка
    ↓
ввод кода
    ↓
Backend
    ↓
Child → Family → Parent(s)
    ↓
Telegram родителя
    ↓
┌───────────────┐
│ Да / Нет      │
└───────────────┘
    ↓
Backend завершает или отклоняет регистрацию
```

Telegram не создаёт `devices` напрямую и не выдаёт долгосрочные device credentials.

---

## 3. Что уже есть в Telegram Bot

Текущий бот построен на Telethon и уже содержит:

- `/start`;
- определение пользователя по Telegram ID;
- регистрацию родителя;
- регистрацию ребёнка через существующий family invite;
- родительское меню;
- детское меню;
- Backend HTTP client;
- state machine регистрации;
- тесты Telegram-слоя.

Следовательно, Telegram Bot не требуется переписывать с нуля.

---

## 4. Главный конфликт текущей регистрации ребёнка с новой схемой

Текущий `registration.py` использует state machine для регистрации ребёнка через семейное приглашение:

```text
waiting_invite_code
        ↓
waiting_child_name
        ↓
completed
```

Это процесс:

```text
Family Invite → создание Child
```

Новая регистрация устройства должна быть отдельным процессом:

```text
Device Registration Request
        ↓
временный код
        ↓
существующий Child
        ↓
Parent Approval
        ↓
Device
```

### Важно

Существующий flow регистрации ребёнка через family invite **не удалять и не заменять** новым device-registration flow.

Это две разные бизнес-задачи.

---

## 5. Child Telegram flow

Для уже зарегистрированного ребёнка должен появиться отдельный путь:

```text
Telegram
  ↓
Устройства
  ↓
Зарегистрировать устройство
  ↓
Ввести код
```

Telegram отправляет на Backend только необходимые данные для идентификации отправителя и код.

Концептуально:

```text
telegram_id
registration_code
```

Telegram не должен принимать от ребёнка как доверенные значения:

```text
family_id
child_id
```

Backend сам определяет:

```text
Telegram ID
    ↓
Child
    ↓
Family
    ↓
active Parent(s)
```

---

## 6. Child menu

Текущее меню ребёнка содержит:

```text
👤 Профиль
⏱ Время
💻 Устройства
```

Раздел `💻 Устройства` сейчас в основном показывает уже зарегистрированные устройства.

Его необходимо расширить концептуально:

```text
💻 Устройства

[зарегистрированные устройства]

[➕ Зарегистрировать устройство]
```

Кнопка не должна сама создавать устройство. Она должна запускать ввод временного кода, полученного ребёнком от Agent.

---

## 7. Child registration state machine

В текущую state machine необходимо добавить отдельный device-registration dialogue.

Концептуальное состояние:

```text
waiting_device_registration_code
```

Возможный flow:

```text
idle
  ↓
waiting_device_registration_code
  ↓
Backend проверяет код
  ├── invalid
  ├── expired
  ├── already used
  └── accepted
          ↓
    waiting_parent_approval
          ↓
    approved / rejected / timeout
```

Точные имена состояний должны быть определены при реализации.

---

## 8. Parent approval flow

Сейчас родительское меню не содержит механизма подтверждения регистрации устройства.

Нужно добавить отдельный Telegram flow:

```text
Backend
   ↓
Telegram Bot
   ↓
Parent
```

Пример логики сообщения:

```text
💻 Запрос на регистрацию устройства

Ребёнок хочет зарегистрировать новое устройство.

Подтвердить регистрацию?

[ ✅ Да ] [ ❌ Нет ]
```

Текст является концептуальным; окончательный UX-текст будет определён при реализации.

---

## 9. Approval callbacks

Для родителя потребуются callback actions, логически соответствующие:

```text
approve registration
reject registration
```

Backend обязан повторно проверить:

- что пользователь является активным родителем;
- что запрос относится к его семье;
- что Registration Request ещё находится в состоянии ожидания;
- что TTL не истёк;
- что запрос не был ранее обработан.

Telegram UI не должен быть источником истины для этих проверок.

---

## 10. Server-originated notification

Новая схема отличается от большинства текущих действий бота тем, что событие возникает не в Telegram:

```text
Child entered code
       ↓
Backend
       ↓
Parent должен получить уведомление
```

Следовательно, нужен механизм:

```text
Backend → Telegram Bot → Parent
```

Это отдельная архитектурная часть и не сводится только к добавлению новой кнопки в меню.

Конкретный механизм доставки уведомления должен быть определён отдельно.

---

## 11. `backend_client.py`

Текущий Telegram `BackendClient` уже умеет работать с:

- поиском Telegram ID;
- регистрацией родителя;
- профилем;
- семьёй;
- детьми;
- семейными приглашениями;
- удалением аккаунта.

Для новой схемы понадобятся новые методы, концептуально:

```text
submit_device_registration_code(...)
get_device_registration_status(...)
approve_device_registration(...)
reject_device_registration(...)
```

Точный набор методов зависит от окончательного Backend API/RPC contract.

Не следует проектировать Telegram Client независимо от backend-контракта.

---

## 12. Backend/Supabase dependency

Live Supabase уже содержит инфраструктуру зарегистрированных устройств:

- `devices`;
- `device_auth_tokens`;
- `authenticate_device`;
- `create_device_auth_token`;
- heartbeat;
- command infrastructure.

Но отдельной сущности `device_registration_requests` и соответствующего lifecycle для нового flow сейчас нет.

Также отсутствуют специализированные операции, концептуально аналогичные:

```text
create device registration request
submit registration code
approve registration
reject registration
```

Поэтому Telegram нельзя реализовать как полностью самостоятельную часть новой схемы: ему нужен согласованный Backend/Supabase contract.

---

## 13. `family_invites` не переиспользовать

Существующий `family_invites` должен продолжить использоваться для семейных приглашений:

```text
Family invitation
→ Child joins family
```

Регистрация устройства должна иметь отдельную сущность:

```text
Device Registration Request
```

Нельзя смешивать:

```text
Family Invite
Device Registration Request
```

в одной бизнес-сущности.

---

## 14. Telegram не создаёт `devices`

После ввода кода Telegram только инициирует серверный процесс.

Правильная последовательность:

```text
Telegram Child
     ↓
Backend
     ↓
Parent Approval
     ↓
Backend
     ↓
create devices
     ↓
create device_auth_tokens
```

Таким образом Telegram не получает права напрямую создавать зарегистрированное устройство.

---

## 15. Timeout

Временный запрос имеет TTL 10 минут.

Если родитель не отвечает:

```text
WAITING_PARENT_APPROVAL
       ↓ 10 min
TIMEOUT
```

Telegram должен корректно сообщить ребёнку результат:

```text
Регистрация не подтверждена вовремя.
Попробуйте начать регистрацию снова.
```

При timeout:

- запрос становится terminal;
- код больше недействителен;
- approval невозможен;
- `devices` не создаётся;
- долгосрочный device token не выдаётся;
- Agent остаётся работоспособным;
- ребёнок может начать новую попытку.

---

## 16. Повторные действия

Telegram должен корректно обрабатывать повторные действия.

Например:

```text
Parent → Да
Parent → Да ещё раз
```

Второй запрос не должен повторно регистрировать устройство.

То же самое:

```text
Parent → Нет
Parent → Да
```

После первого terminal decision второе действие должно быть отклонено Backend.

## 18. Что не менять на этом этапе

В рамках Telegram-этапа не требуется менять смысл или архитектуру:

- `devices`;
- `device_auth_tokens`;
- device authentication;
- heartbeat;
- command infrastructure;
- update infrastructure;
- `family_invites`.

Также не следует удалять существующую регистрацию ребёнка через family invite.

## 20. Зависимости этапов

Новая реализация должна идти в следующем порядке:

```text
1. Зафиксировать Backend/Supabase contract
            ↓
2. Добавить Telegram Client methods
            ↓
3. Добавить child code flow
            ↓
4. Добавить parent approval UI
            ↓
5. Добавить server-originated notification
            ↓
6. Добавить тесты
            ↓
7. Провести сквозной тест с Agent + Backend + Supabase
```

Telegram-часть не должна самостоятельно придумывать состояние Registration Request, если оно ещё не закреплено в Backend/Supabase.

---

## 21. Итог

Telegram Bot уже имеет устойчивую основу и не требует переписывания.

Для новой схемы необходимо добавить **отдельный device-registration flow**, не затрагивая семантику существующей регистрации ребёнка и family invites.

Главные изменения:

1. ребёнок вводит в Telegram временный код, полученный от Agent;
2. Backend определяет Child → Family → Parent(s);
3. родитель получает запрос в Telegram;
4. родитель выбирает `Да` или `Нет`;
5. Telegram отображает состояние результата;
6. Backend остаётся источником истины;
7. `devices` и долгосрочные credentials создаются только после approval;
8. timeout составляет 10 минут;
9. повторные решения после terminal state запрещены;
10. family invites остаются отдельным механизмом.

Главный технический вывод этапа:

> **Сначала необходимо определить и реализовать серверную сущность Registration Request и её API/RPC-контракт, после чего Telegram Bot сможет безопасно реализовать новый пользовательский flow.**

Никаких изменений кода или Supabase в рамках данного анализа не выполнялось.
