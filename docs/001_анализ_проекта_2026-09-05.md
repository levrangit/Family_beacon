# Анализ проекта Family Beacon

**Дата:** 05.09.2026  
**Ветка:** `develop`  
**Текущий commit:** `7abaaeaa3a7457367c8aa85c41d5dcb6aefb4faf`  

## 1. Общая оценка

Текущее состояние проекта оценивается примерно как **7/10 для рабочего прототипа** и **5/10 для production-ready системы**.

Архитектурная основа проекта хорошая: Telegram-бот не должен напрямую работать с Supabase, Backend выступает центральным API, отдельно развиваются Device Agent и Frontend.

Основной риск сейчас связан не с отсутствием архитектуры, а с разной степенью готовности отдельных частей системы.

## 2. Архитектура

Основная схема:

```text
Telegram / Telethon
        ↓
   Telegram Bot
        ↓
     Backend API
        ↓
     Supabase
        ↑
 Device Agent
```

Архитектура хорошо разделяет ответственность между компонентами.

### Оценка: 8/10

## 3. Supabase

Схема уже достаточно зрелая и включает:

- profiles;
- families;
- family_members;
- children;
- devices;
- time_policies;
- time_usage;
- commands;
- audit_log;
- family_invites;
- device authentication и heartbeat;
- recovery;
- Telegram IDs;
- parent account deletion.

Migration-файлы являются источником истины для схемы, что соответствует правилам проекта.

### Сильные стороны

- PostgreSQL/Supabase используется последовательно;
- SQLite не используется;
- присутствуют внешние ключи;
- присутствуют индексы;
- используется RLS;
- есть SECURITY DEFINER RPC-функции для отдельных операций;
- операции redeem invite реализованы атомарно.

### Оценка: 8/10

## 4. Supabase Security

Это одна из главных зон технического долга.

Security Advisor показывает предупреждения, связанные с SECURITY DEFINER-функциями и их правами EXECUTE. Особенно внимательно необходимо проверить функции, связанные с device authentication, command queue, heartbeat, family invites и удалением аккаунта.

Рекомендуемое направление:

```text
SECURITY DEFINER
        ↓
проверка реальной необходимости EXECUTE
        ↓
REVOKE лишних прав
        ↓
GRANT только необходимым ролям
```

Это следует выполнять отдельными migration-файлами и сначала проверять локально.

Также рекомендуется включить Leaked Password Protection в Supabase Auth перед production.

### Оценка: 5/10

## 5. Performance

Критических проблем производительности не выявлено.

Advisor указывает, среди прочего, на:

- foreign key без отдельного индекса для `commands.created_by`;
- оптимизацию некоторых RLS policies с `auth.uid()` через initplan;
- несколько пока неиспользуемых индексов.

Удалять неиспользуемые индексы прямо сейчас не рекомендуется: проект активно развивается, и часть индексов может понадобиться будущим функциям.

### Оценка: 7/10

## 6. Telegram Bot

Родительский flow уже имеет рабочую основу:

- `/start`;
- определение Telegram ID;
- родительское меню;
- профиль;
- семья;
- дети;
- создание приглашения;
- список приглашений;
- удаление аккаунта.

Invite flow умеет создавать код, хранить его и показывать родителю.

Формат даты теперь отображается как:

```text
Действует до: 05.09.2026
```

### Главный незавершённый участок

Регистрация ребёнка пока не реализована в полном виде. При выборе роли ребёнка бот сообщает о следующем шаге, но полноценного сценария:

```text
Ребёнок
   ↓
Имя
   ↓
Invite Code
   ↓
проверка invite
   ↓
children
   ↓
Telegram ID
   ↓
Child Menu
```

пока нет.

### Оценка: 6/10

## 7. Важное расхождение в invite-модели

Нужно отдельно решить архитектурное расхождение.

Документ архитектуры описывает invite как механизм регистрации ребёнка. Однако текущая Supabase-функция `redeem_family_invite()` при успешном redeem добавляет пользователя в `family_members` с `member_type = 'parent'`.

То есть фактическое поведение сейчас:

```text
Invite
   ↓
authenticated user
   ↓
family_members
   ↓
parent
```

а ожидаемая по архитектуре модель выглядит как:

```text
Invite
   ↓
child registration
   ↓
children
   ↓
Child Menu
```

Это следует исправлять только после принятия окончательного решения о модели регистрации ребёнка.

## 8. Invite Code и безопасность

Первоначальная модель `family_invites` хранила только `code_hash`, что является более безопасным вариантом.

Для возможности показывать старые приглашения родителю позже был добавлен `code`.

Теперь в базе присутствуют оба значения:

```text
code_hash  — проверка кода
code       — отображение кода родителю
```

Это рабочий компромисс, но для production следует дополнительно оценить необходимость хранения открытого invite code.

## 9. Backend

Backend уже представляет собой полноценный API layer на FastAPI.

В нём присутствуют маршруты для:

- authentication;
- families;
- children;
- devices;
- time policies;
- time usage;
- commands;
- Telegram parent operations;
- device heartbeat;
- device command queue;
- invites.

Хорошим решением является использование HMAC-сравнения для Telegram shared secret.

### Оценка: 8/10

## 10. Device Agent

Agent имеет command abstraction и отдельную реализацию Windows app blocker.

Уже предусмотрены команды:

- get_status;
- lock;
- shutdown;
- restart;
- sleep;
- get_device_state;
- set_time_limit;
- block_app;
- unblock_app.

Есть значительный набор тестов.

При этом часть функций пока является подготовкой к полноценной системной реализации. Например `set_time_limit` ещё не представляет полностью реализованное production-ограничение системного времени.

### Оценка: 7/10

## 11. Frontend

Frontend пока в значительной степени является UI-прототипом.

Часть операций работает через локальное React state и демонстрирует будущую функциональность, но ещё не весь UI проходит полноценный путь:

```text
Frontend
   ↓
Backend
   ↓
Supabase
   ↓
Device Agent
```

Поэтому текущий frontend не следует считать полностью production-интерфейсом.

### Оценка: 6/10

## 12. CI/CD и тестирование

В проекте есть отдельные GitHub Actions для backend, Supabase и SonarQube.

Supabase workflow проверяет применение миграций локально. Backend workflow запускает pytest и проверяет health endpoint.

Также существует существенный набор unit-тестов для backend, Telegram и Device Agent.

Последняя целевая проверка Telegram/invite набора дала:

```text
13 passed
```

Следующим этапом желательно увеличивать integration/E2E coverage, а не только количество unit-тестов.

### Оценка: 8/10

## 13. Production readiness

Проект пока не готов к полноценному production release.

Основные причины:

1. не завершён Child Registration;
2. есть расхождение между архитектурой invite и фактической моделью redeem;
3. необходимо провести Supabase security hardening;
4. frontend ещё не полностью интегрирован с backend;
5. Device Agent требует доведения ряда функций до production behavior;
6. отсутствует полноценный release/update/rollback контур.

### Оценка: 5/10

## 14. Приоритет дальнейшей разработки

Рекомендуемый порядок:

### Этап 1 — Child Registration

Реализовать полный сценарий регистрации ребёнка через invite code.

### Этап 2 — Security hardening Supabase

Проверить все SECURITY DEFINER функции и права EXECUTE.

### Этап 3 — Frontend ↔ Backend

Перевести mock/local state на реальные backend operations.

### Этап 4 — Device Agent

Довести реальные системные операции, heartbeat, recovery и ограничения приложений/времени.

### Этап 5 — Release / Update Service

После стабилизации основного функционала реализовать release, distribution, health check и rollback.

### Главный вывод

Family Beacon уже имеет хорошую техническую основу и может развиваться как единая система. Главный следующий шаг — не расширять функциональность хаотично, а сначала определить и реализовать корректную модель Child Registration и привести invite flow к этой модели.

После этого имеет смысл заняться security hardening Supabase и только затем активно расширять frontend и production-контур.
