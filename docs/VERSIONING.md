# Family Beacon — Versioning Policy

## 1. Версия проекта

Family Beacon использует **Semantic Versioning (SemVer)**:

```text
MAJOR.MINOR.PATCH
```

Текущая версия продукта хранится в корневом файле `VERSION` без префикса `v`.

Пример:

```text
0.1.0
```

В Git, Release и пользовательских обозначениях версия записывается с префиксом `v`:

```text
v0.1.0
```

Файл `VERSION` является единым источником текущей версии **продукта Family Beacon**.

---

## 2. Правила изменения версии

### MAJOR

Увеличивается при несовместимом изменении архитектуры, API, модели данных или другого публичного контракта проекта.

```text
v1.4.2 → v2.0.0
```

### MINOR

Увеличивается при добавлении новой функциональности без намеренного нарушения существующей совместимости.

```text
v0.1.0 → v0.2.0
```

### PATCH

Увеличивается при исправлениях ошибок, небольших улучшениях и других изменениях, не добавляющих новую значимую функциональность.

```text
v0.2.0 → v0.2.1
```

---

## 3. Версия продукта и версии компонентов

Family Beacon является составным продуктом.

Версия продукта и версии отдельных компонентов являются разными понятиями.

Пример:

```text
Family Beacon v0.5.0

Backend       0.5.0
Telegram Bot  0.5.0
Frontend      0.4.2
Device Agent  0.3.1
Update        0.2.0
```

Версия продукта определяет версию Family Beacon в целом.

Каждый программный компонент может иметь собственную версию и обновляться независимо от других компонентов.

Изменение версии одного компонента не требует автоматического изменения версий всех остальных компонентов.

Например:

```text
Family Beacon v0.5.1

Backend       0.5.1
Telegram Bot  0.5.0
Frontend      0.4.2
Device Agent  0.3.1
```

Такое состояние является допустимым.

---

## 4. Release

**Release** — опубликованная версия продукта, содержащая конкретный набор версий компонентов.

Например:

```text
Release v0.5.0

Backend       0.5.0
Telegram Bot  0.5.0
Frontend      0.4.2
Device Agent  0.3.1
Update        0.2.0
```

Release фиксирует согласованное состояние продукта и определяет, какие версии компонентов относятся к данной версии Family Beacon.

Release является основанием для последующего процесса обновления работающих компонентов.

---

## 5. Git tags

Для версии продукта используется Git tag:

```text
vMAJOR.MINOR.PATCH
```

Например:

```text
v0.1.0
v0.2.0
v0.2.1
```

Номер Git tag должен совпадать с версией продукта в `VERSION`.

Git tag фиксирует конкретное состояние исходного кода в Git.

Git tag не является непосредственно пакетом обновления.

---

## 6. Update Package

**Update Package** — опубликованный пакет, предназначенный для установки конкретной версии компонента.

Например:

```text
Device Agent 0.3.1
    ↓
Update Package
    ↓
FamilyBeaconAgent.exe
```

Git tag фиксирует исходный код.

Release фиксирует опубликованную версию продукта.

Update Package содержит программный компонент, который может быть доставлен работающей системе через Update System.

Компонент не должен считать наличие нового Git tag основанием для непосредственной загрузки и запуска исходного кода.

Получение и установка обновлений выполняются через предусмотренную архитектурой систему обновлений.

---

## 7. Version и Update System

Процесс разработки и процесс обновления являются разными этапами жизненного цикла версии.

Общий процесс:

```text
feature / fix
      ↓
   develop
      ↓
   CI + tests
      ↓
     PR
      ↓
    main
      ↓
  Release vX.Y.Z
      ↓
 Update System
      ↓
 Update Manifest
      ↓
 Component Update
      ↓
 verification
      ↓
 installation
      ↓
 Health Check
      ↓
 SUCCESS / ROLLBACK
```

Versioning отвечает на вопрос:

> Какая это версия?

Update Architecture отвечает на вопрос:

> Как доставить и безопасно установить эту версию на работающий компонент?

Подробные правила процесса обновления определяются документом:

```text
docs/UPDATE_ARCHITECTURE.md
```

---

## 8. Версия компонента при обновлении

Каждый обновляемый компонент должен однозначно идентифицироваться своим именем и версией.

Например:

```text
component: device-agent
version: 0.3.1
```

Device Agent должен сообщать Backend свою фактическую установленную версию.

Например:

```text
Family Beacon: v0.5.0
Device Agent:  0.3.1
```

Это необходимо для:

- определения доступных обновлений;
- проверки совместимости;
- выбора целевой версии;
- контроля rollout;
- диагностики;
- истории обновлений.

---

## 9. Совместимость версий

Номер версии сам по себе не гарантирует совместимость двух компонентов.

Совместимость определяется отдельной **Compatibility Matrix**.

Например:

```text
Backend 0.4.x + Agent 0.3.x = supported
Backend 0.5.x + Agent 0.3.x = supported
Backend 0.5.x + Agent 0.2.x = warning
Backend 0.6.x + Agent 0.2.x = unsupported
```

Compatibility Matrix определяет, какие комбинации версий компонентов могут использоваться совместно.

Правила совместимости являются частью Release и Update Architecture.

---

## 10. Baseline

Baseline — это проверенная контрольная точка проекта.

Для каждой официально зафиксированной версии baseline имеет имя:

```text
baseline-vMAJOR.MINOR.PATCH
```

Например:

```text
baseline-v0.1.0
baseline-v0.2.0
baseline-v0.2.1
```

Номер baseline всегда совпадает с номером версии продукта.

Baseline создаётся только после завершения логического этапа разработки и соответствующей проверки проекта.

Baseline фиксирует состояние проекта, которое считается проверенным и пригодным для дальнейшего развития или использования как контрольной точки.

---

## 11. Коммиты и версии

Не каждый коммит создаёт новую версию или baseline.

Обычные коммиты могут находиться между версиями:

```text
commit
commit
commit
    ↓
v0.2.0
    ↓
baseline-v0.2.0
```

Версия отражает состояние продукта.

Commit отражает отдельное изменение в Git.

Компонентная версия отражает состояние конкретного компонента.

Release объединяет версии компонентов в конкретное опубликованное состояние продукта.

---

## 12. Changelog

История изменений проекта ведётся в корневом файле:

```text
CHANGELOG.md
```

Для каждой официальной версии создаётся отдельный раздел с номером версии и датой.

Changelog должен описывать изменения продукта и, при необходимости, существенные изменения отдельных компонентов.

---

## 13. Связь Release, Baseline и Update

Release и Baseline имеют разные назначения.

```text
Release
  ↓
опубликованная версия продукта
  ↓
может быть доставлена через Update System


Baseline
  ↓
проверенная контрольная точка исходного кода
```

Baseline не является отдельным типом Update Package.

Update System использует опубликованные Release и связанные с ними компоненты, пакеты и метаданные обновления.

---

## 14. Что может обновляться

В рамках архитектуры Family Beacon обновляться могут отдельные программные компоненты:

```text
Backend
Telegram Bot
Frontend
Device Agent
Update Service
```

При этом не каждый компонент обязан обновляться при каждом новом Release.

Например:

```text
Release v0.5.0

Backend       → 0.5.0
Telegram Bot  → 0.5.0
Frontend      → 0.4.2
Device Agent  → 0.3.1
```

Update System определяет, какие компоненты нуждаются в обновлении.

---

## 15. Supabase и версии

Изменения схемы Supabase не относятся к обычному механизму обновления программных компонентов.

Изменения базы данных выполняются через migration workflow.

Порядок:

```text
migration
    ↓
local Supabase
    ↓
local verification
    ↓
migration workflow
    ↓
remote Supabase
```

Migration-файлы в:

```text
supabase/migrations/
```

являются источником истины для схемы Supabase.

Изменение схемы не должно выполняться через произвольное прямое изменение remote database.

---

## 16. Baseline checklist

Перед созданием нового baseline необходимо:

1. завершить соответствующий этап разработки;
2. определить новую версию продукта;
3. обновить `VERSION`;
4. обновить `CHANGELOG.md`;
5. определить версии компонентов, входящих в Release;
6. выполнить необходимые тесты и проверки;
7. проверить совместимость компонентов;
8. убедиться, что рабочее дерево Git чистое;
9. создать Git tag `vMAJOR.MINOR.PATCH`;
10. создать Git tag `baseline-vMAJOR.MINOR.PATCH`;
11. отправить оба tag в remote repository.

Теги не следует перезаписывать или принудительно перемещать после создания baseline.

---

## 17. Первый официальный baseline

Новая система версионирования Family Beacon начинается с:

```text
v0.1.0
baseline-v0.1.0
```

Версия `0.x` означает, что проект находится в активной стадии разработки и его API, архитектура и функциональность ещё могут существенно изменяться до первой стабильной версии:

```text
v1.0.0
```

---

## 18. Исторический baseline

До введения данной системы в проекте существовал датированный tag:

```text
baseline-2026-09-05
```

Он сохраняется как историческая точка и не переименовывается.

Новые baseline должны использовать только формат:

```text
baseline-vMAJOR.MINOR.PATCH
```

---

## 19. Главный принцип версионирования

Family Beacon использует несколько уровней идентификации:

```text
Product Version
      ↓
Release
      ↓
Component Versions
      ↓
Update Packages
```

При этом:

```text
Git Commit
    ≠
Git Tag
    ≠
Release
    ≠
Baseline
    ≠
Update Package
```

Каждый из этих объектов имеет собственное назначение.

Версия должна однозначно определять состояние продукта или конкретного компонента и не должна зависеть от даты, номера коммита или случайного имени файла.
