# Регистрация устройства — этап 1

**Дата:** 2026-09-05  
**Проект:** Family Beacon  
**Рабочая ветка:** `develop`

## 1. Цель этапа

Зафиксировать согласованную архитектуру регистрации нового устройства ребёнка через Telegram-бота, backend и существующую модель `family_invites`.

На этом этапе код и миграции не разрабатываются. Документ фиксирует архитектурные решения, которые должны быть использованы при последующей реализации.

## 2. Общий сценарий

Регистрация устройства инициируется родителем из Telegram-бота:

```text
Моя семья
   ↓
Ребёнок
   ↓
Устройства
   ↓
➕ Добавить устройство
```

Родитель выбирает конкретного ребёнка. Backend создаёт приглашение на регистрацию устройства, которое однозначно связано с выбранными `family_id` и `child_id`.

Agent не передаёт `family_id` или `child_id`. Эти значения всегда определяются backend по приглашению.

После получения pairing code Agent обращается к backend. При первом обращении приглашение переводится из `new` в `pending`. Родителю в Telegram отправляется запрос на подтверждение.

Родитель выбирает:

```text
⚠️ Регистрация устройства

Ребёнок: Иван
Устройство: Ivan-PC
Платформа: Windows

Разрешить?

[Да] [Нет]
```

При подтверждении backend атомарно создаёт устройство и device token, после чего приглашение становится `used`. Agent получает свой device token, сохраняет его и прекращает polling по pairing code.

Parent JWT никогда не передаётся Agent.

Agent не создаёт device token самостоятельно.

Backend создаёт device ID и device token.

## 3. Использование `family_invites`

Для регистрации устройства не создаётся отдельная таблица pairing sessions.

Используется существующая таблица `family_invites` как универсальная модель приглашений.

Pairing code хранится в существующем поле:

```text
family_invites.code
```

`code_hash` продолжает использоваться для серверной проверки кода.

Новые поля `device_code` или `pairing_code` не добавляются.

## 4. Тип приглашения

Вводится универсальный `invite_type` со значениями:

```text
member
child
device
```

Назначение:

- `member` — приглашение нового родителя в семью;
- `child` — приглашение/регистрация ребёнка;
- `device` — приглашение конкретного устройства конкретного ребёнка.

Существующая логика member/child должна продолжить работать после введения универсального типа.

## 5. Статус приглашения

Вводится универсальный `invite_status` со значениями:

```text
new
pending
approved
rejected
used
expired
revoked
```

Смысл статусов:

- `new` — приглашение создано, операция ещё не начиналась;
- `pending` — операция началась и ожидает действия;
- `approved` — родитель явно разрешил операцию;
- `rejected` — родитель явно отклонил операцию;
- `used` — операция успешно завершена;
- `expired` — срок действия приглашения истёк;
- `revoked` — приглашение отозвано.

### Статусы для устройства

Основной переход:

```text
new → pending → approved → used
```

Отказ:

```text
new/pending → rejected
```

Истечение срока:

```text
new/pending → expired
```

Отзыв:

```text
new/pending → revoked
```

### Статусы для существующих типов

Member:

```text
new → used
```

Child:

```text
new → used
```

## 6. Привязка устройства к ребёнку

При создании device invite backend получает выбранные родителем:

- `family_id`;
- `child_id`.

Эти значения сохраняются в приглашении.

Agent не должен присылать их в запросах.

При успешном завершении pairing backend получает `family_id` и `child_id` из самого приглашения и использует их при создании записи в `devices`.

Это исключает возможность подмены ребёнка или семьи со стороны Agent.

## 7. Срок действия pairing code

TTL приглашения устройства:

```text
10 минут
```

После истечения TTL приглашение не может быть использовано для регистрации устройства.

`expires_at` остаётся обязательной серверной проверкой независимо от значения `invite_status`.

## 8. Одноразовость

Pairing invite является одноразовым.

После успешной регистрации:

```text
invite_status = used
used_at = текущая дата/время
```

Повторное использование такого приглашения запрещено.

Для device invite существующее поле `used_by` не используется для хранения `device_id`, поскольку оно ссылается на `profiles(id)`.

Для устройства достаточно:

```text
used_at = timestamp
used_by = NULL
```

Идентификатор созданного устройства при необходимости фиксируется через audit log.

## 9. API

Предпочтительный вариант API состоит из двух endpoint'ов.

### Запуск pairing

```http
POST /devices/pair
```

Пример тела запроса:

```json
{
  "code": "ABCD-7K9P",
  "hostname": "Ivan-PC",
  "platform": "windows",
  "agent_version": "1.0.0"
}
```

Назначение:

- найти приглашение по hash pairing code;
- проверить срок действия и возможность использования;
- при первом обращении перевести `new → pending`;
- зафиксировать сведения об устройстве;
- инициировать уведомление родителя;
- вернуть Agent текущий статус pairing.

### Проверка статуса

```http
POST /devices/pair/status
```

Пример:

```json
{
  "code": "ABCD-7K9P"
}
```

Pairing code не передаётся через URL или query parameters, поскольку он является временным секретом и не должен без необходимости попадать в URL/proxy logs.

## 10. Polling Agent

Agent после запуска pairing периодически проверяет состояние операции.

Интервал polling — отдельная настройка проекта:

```text
FAMILY_BEACON_PAIRING_POLL_INTERVAL_SECONDS=10
```

Начальное значение:

```text
10 секунд
```

Эта настройка отделяется от обычного рабочего polling/heartbeat интервала Agent.

После получения финального результата (`approved`, `rejected`, `expired`, `revoked` или успешного `used`) Agent прекращает pairing polling.

При успешном завершении Agent получает device token и далее работает только через обычный device authentication flow.

## 11. Защита от перебора pairing code

На первом этапе отдельный rate limiting не добавляется.

Используется существующая длина/энтропия pairing code в сочетании с:

- криптографически безопасной генерацией кода;
- TTL 10 минут;
- одноразовостью приглашения;
- обязательным подтверждением родителем.

Rate limiting может быть добавлен отдельным этапом позднее.

## 12. Device token

Device token не создаётся Agent.

После подтверждения родителем backend должен:

1. создать запись `devices`;
2. создать device authentication token;
3. сохранить только необходимое представление токена/его hash согласно существующей архитектуре;
4. вернуть Agent его device token;
5. завершить приглашение.

Parent JWT и Telegram credentials в Agent не передаются.

## 13. Атомарное завершение регистрации

Для финальной операции предусматривается отдельная привилегированная операция, условно:

```text
redeem_device_invite
```

Операция должна выполняться атомарно.

Логическая последовательность:

```text
BEGIN
  заблокировать и проверить invite
  проверить invite_type = device
  проверить invite_status = approved
  проверить expires_at > now()
  проверить invite не использован и не отозван
  получить family_id и child_id из invite
  создать devices
  создать device auth token
  пометить invite как used
  записать audit log
COMMIT
```

При любой ошибке вся операция откатывается.

Необходимо обеспечить защиту от гонок при одновременной обработке одного приглашения, например через блокировку строки (`FOR UPDATE`) и повторную проверку состояния внутри транзакции.

## 14. Права `redeem_device_invite`

Предпочтительная модель:

```text
SECURITY DEFINER
set search_path = public
REVOKE ALL
GRANT EXECUTE ... TO service_role
```

Итоговая операция создания устройства не должна быть доступна `anon`.

Agent не должен иметь возможность самостоятельно вызвать привилегированную операцию создания устройства только по pairing code.

Backend после подтверждения родителем использует service-role клиент для выполнения привилегированной операции.

## 15. Текущая модель `family_invites` и совместимость

В текущей схеме уже существуют:

```text
id
family_id
created_by
code_hash
expires_at
used_at
used_by
revoked_at
created_at
code
used_by_child
```

Новая архитектура должна расширить эту модель, не ломая существующие member/child flows.

Особое внимание требуется уделить старым строкам `family_invites`, созданным до появления `invite_type`.

Существующие записи не обязательно содержат явный признак, был ли это member invite или child invite. Поэтому перед миграцией необходимо фактически проверить legacy-данные и только после этого определить безопасную стратегию заполнения `invite_type`.

Нельзя автоматически классифицировать старые записи только на основании предположения.

## 16. Текущие существующие RPC и их изменения

После введения `invite_type` существующие операции должны явно проверять соответствующий тип приглашения.

### Member

`redeem_family_invite` должен принимать только:

```text
invite_type = member
```

### Child

`register_child_by_invite` должен принимать только:

```text
invite_type = child
```

### Device

Новая операция:

```text
redeem_device_invite
```

должна работать только с:

```text
invite_type = device
```

Это предотвращает использование приглашения одного типа в flow другого типа.

## 17. Создание device invite

Для device invite предпочтительно иметь отдельную внутреннюю операцию создания приглашения, а не ломать существующую сигнатуру:

```text
create_family_invite(
    p_family_id,
    p_code_hash,
    p_expires_at
)
```

Причина — существующий member flow уже использует эту операцию, а child invite сейчас также имеет отдельную реализацию.

Device invite должен создаваться backend-слоем с указанием:

```text
invite_type = device
invite_status = new
family_id = выбранная семья
child_id = выбранный ребёнок
expires_at = now() + 10 minutes
code = plaintext pairing code
code_hash = hash pairing code
```

## 18. Рекомендуемый порядок реализации

Реализация должна выполняться последовательно.

### Шаг 1 — проверить legacy invites

Перед изменением схемы получить из Supabase только безопасные метаданные существующих `family_invites`:

- `id`;
- `family_id`;
- наличие `used_at`;
- наличие `used_by`;
- наличие `used_by_child`;
- `expires_at`;
- наличие `revoked_at`;
- `created_at`.

Не выводить и не раскрывать `code` или `code_hash`.

Цель — определить, как безопасно классифицировать существующие записи после введения `invite_type`.

### Шаг 2 — migration 031

Следующей миграцией после текущих 001–030 предполагается миграция:

```text
031_device_invite_status.sql
```

Название является рабочим и может быть уточнено до создания файла миграции.

В ней предполагается:

1. добавить enum `invite_type`;
2. добавить enum `invite_status`;
3. добавить необходимые колонки в `family_invites`;
4. безопасно мигрировать legacy rows;
5. добавить необходимые constraints;
6. сохранить совместимость существующих member/child flows.

### Шаг 3 — обновить существующие RPC

- `redeem_family_invite` → только `member`;
- `register_child_by_invite` → только `child`.

### Шаг 4 — добавить device invite creation

Создание приглашения с:

```text
invite_type = device
invite_status = new
child_id = выбранный ребёнок
TTL = 10 минут
```

### Шаг 5 — добавить device pairing API

Реализовать:

```text
POST /devices/pair
POST /devices/pair/status
```

### Шаг 6 — добавить parent approval flow

Telegram-бот показывает родителю сведения об устройстве и предоставляет кнопки:

```text
[Да] [Нет]
```

При `Да` состояние переводится в `approved`, после чего выполняется привилегированное атомарное завершение pairing.

При `Нет` состояние переводится в `rejected`.

### Шаг 7 — Agent pairing flow

Agent:

1. получает pairing code;
2. вызывает `POST /devices/pair`;
3. получает `pending`;
4. каждые 10 секунд вызывает `POST /devices/pair/status`;
5. ждёт решения родителя;
6. при approval получает device token;
7. сохраняет device token;
8. прекращает pairing polling;
9. переходит к обычной работе.

### Шаг 8 — тесты

Необходимо покрыть как минимум:

- создание device invite;
- правильную привязку к `family_id` и `child_id`;
- `new → pending` при первом обращении Agent;
- повторное обращение Agent;
- approval;
- rejection;
- expiration;
- revoke;
- повторное использование после `used`;
- попытку использовать member/child invite в device flow;
- отсутствие возможности подменить `child_id` или `family_id` через Agent;
- атомарность создания device + token + завершения invite;
- конкурентные запросы к одному invite;
- отсутствие передачи parent JWT Agent;
- корректную работу `FAMILY_BEACON_PAIRING_POLL_INTERVAL_SECONDS`.

## 19. Что пока НЕ добавляется

На этом этапе не добавляются:

- отдельная таблица `device_pairing_sessions`;
- отдельное поле `device_code`;
- отдельное поле `pairing_code`;
- передача `child_id` от Agent;
- передача `family_id` от Agent;
- передача parent JWT Agent;
- генерация device token на Agent;
- отдельный rate limiting для pairing code.

## 20. Зафиксированная архитектурная модель

Итоговая схема:

```text
Parent (Telegram)
      │
      │ выбирает ребёнка
      ▼
Backend
      │
      │ создаёт device invite
      │ invite_type=device
      │ invite_status=new
      │ child_id=<selected child>
      │ family_id=<selected family>
      │ TTL=10 min
      ▼
family_invites
      │
      │ pairing code
      ▼
Agent
      │
      │ POST /devices/pair
      ▼
invite_status: new → pending
      │
      │ уведомление родителю
      ▼
Telegram Parent
      │
      ├── Нет → rejected
      │
      └── Да → approved
                  │
                  ▼
        redeem_device_invite
                  │
                  ├── create devices
                  ├── create device token
                  ├── audit log
                  └── invite → used
                  │
                  ▼
                Agent
                  │
                  └── получает device token
                      и переходит к обычной работе
```

## 21. Состояние на конец этапа

На конец этого этапа архитектурные решения зафиксированы.

Код, миграция `031` и runtime-изменения Agent/Telegram backend на этом этапе ещё не реализуются автоматически только на основании данного документа.

Перед реализацией необходимо сначала проверить фактические legacy-данные `family_invites` в Supabase и затем подтвердить окончательный SQL-план миграции.
