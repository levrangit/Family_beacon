# Правила организации тестов Family Beacon

## 1. Назначение

Этот файл является манифестом правил организации тестов проекта Family Beacon. Он определяет, где должны находиться тесты разных уровней и как отделять тестовую инфраструктуру от самих тестов.

Главная цель — не смешивать unit, API, contract, integration и E2E тесты в одном каталоге и сделать структуру тестов предсказуемой.

## 2. Основное правило структуры

Первый уровень каталогов `backend/tests/` определяется **типом теста**, второй — **областью системы**.

Рекомендуемая структура:

```text
backend/tests/
│
├── conftest.py
│
├── support/
│   └── auth/
│       ├── client.py
│       └── users.py
│
├── unit/
│   ├── auth/
│   ├── children/
│   ├── commands/
│   ├── devices/
│   ├── family/
│   ├── policies/
│   ├── registration/
│   ├── usage/
│   └── updates/
│
├── api/
│   ├── auth/
│   ├── devices/
│   ├── device_updates/
│   ├── family/
│   ├── invites/
│   ├── registration/
│   └── usage/
│
├── contracts/
│   ├── auth/
│   └── devices/
│
├── integration/
│   └── invites/
│
└── e2e/
    └── invites/
```

Папки создаются по мере появления соответствующих тестов. Не следует создавать пустые каталоги только ради симметрии.

## 3. Unit-тесты

Каталог: `backend/tests/unit/`

Unit-тест проверяет изолированную бизнес-логику или функцию.

Правила:

- не создавать реальные записи в удалённой Supabase;
- не создавать реальные Auth users;
- не зависеть от внешней инфраструктуры;
- использовать mocks/fakes/stubs там, где это необходимо;
- тестировать одну логическую область.

Примеры областей:

```text
unit/auth/
unit/children/
unit/commands/
unit/devices/
unit/family/
unit/policies/
unit/registration/
unit/usage/
unit/updates/
```

## 4. API-тесты

Каталог: `backend/tests/api/`

API-тест проверяет HTTP endpoint и его контракт на уровне приложения.

Правила:

- проверять HTTP method, path, status code и структуру ответа;
- отдельно проверять входные данные и ошибки валидации;
- не смешивать API-проверку с полноценным E2E-сценарием;
- если тест требует реальной удалённой Supabase, его классификация должна быть пересмотрена как integration/E2E.

## 5. Contract-тесты

Каталог: `backend/tests/contracts/`

Contract-тест проверяет соглашение между компонентами системы: формат запроса, ответа, сообщения или другого интерфейса взаимодействия.

Contract-тесты не должны превращаться в полноценные integration/E2E сценарии.

Примеры:

```text
contracts/auth/
contracts/devices/
```

## 6. Integration-тесты

Каталог: `backend/tests/integration/`

Integration-тест проверяет взаимодействие нескольких реальных компонентов системы.

Особенно важно отделять такие тесты от unit/API тестов, если они создают реальные данные в удалённой Supabase.

Правила для тестов с реальной Supabase:

1. Требуемая инфраструктура должна быть обязательной.
2. Если необходимые credentials/infrastructure отсутствуют, тест должен **FAIL**, а не SKIP.
3. Тест должен удалять все созданные данные.
4. Cleanup должен выполняться через `finally`.
5. Ошибка Cleanup должна приводить к **FAIL**, а не подавляться.
6. Не следует оставлять тестовые записи в удалённой базе после успешного или неуспешного теста.
7. Секреты и credentials никогда не выводятся в логи.

Для integration-тестов с удалённой Supabase особенно важно сохранять идентификаторы созданных сущностей и удалять их в обратном порядке зависимостей.

## 7. E2E-тесты

Каталог: `backend/tests/e2e/`

E2E-тест проверяет полный пользовательский или системный сценарий через несколько компонентов.

Real E2E должны быть явно opt-in:

```text
RUN_REAL_E2E != 1
    -> SKIP

RUN_REAL_E2E == 1
    -> требуемая инфраструктура отсутствует: FAIL
    -> тест
    -> обязательный Cleanup
    -> ошибка Cleanup: FAIL
```

Таким образом, обычный `pytest` не должен случайно запускать реальные E2E-сценарии и создавать реальные данные.

## 8. Тестовая инфраструктура

Файлы, которые помогают создавать клиентов, пользователей или тестовое окружение, но сами не являются тестами, должны находиться в `support/` либо в другом явно обозначенном инфраструктурном каталоге.

Например:

```text
backend/tests/support/auth/client.py
backend/tests/support/auth/users.py
```

`conftest.py` остаётся в корне `backend/tests/`, если fixtures являются общими для всего backend test suite.

## 9. Регистрация родителя

Тесты регистрации родителя разделяются по уровню:

```text
unit/registration/
    test_parent_registration_profile.py
    test_parent_registration_service.py

api/registration/
    test_parent_registration_contract.py
    test_parent_registration_endpoint.py
```

Логика регистрации и HTTP API не должны находиться в одном тестовом файле только из-за общей предметной области.

## 10. Приглашения

Приглашения имеют несколько разных уровней тестирования:

```text
unit/family/
api/invites/
integration/invites/
e2e/invites/
```

Особенно важно не смешивать тесты, которые работают только с бизнес-логикой, с тестами, которые создают реальные family/invite/Auth записи.

## 11. Telegram Bot и Device Agent

Тестовые контуры разных приложений не объединяются.

```text
backend/tests/        -> Backend
telegram_bot/tests/   -> Telegram Bot
agent/tests/           -> Device Agent
```

Внутри каждого приложения допускается собственная классификация тестов.

Для Telegram Bot рекомендуется:

```text
telegram_bot/tests/
├── unit/
├── menus/
└── registration/
```

Для Device Agent тесты остаются в `agent/tests/` и не переносятся в `backend/tests/`.

## 12. Правила именования

Имя тестового файла должно отражать предмет тестирования и не должно искусственно объединять разные уровни тестов.

Предпочтительно:

```text
test_<component>_service.py
test_<component>_api.py
test_<scenario>_integration.py
test_<scenario>_e2e.py
```

При переносе файлов не следует менять их содержимое без отдельной необходимости.

## 13. Правила наведения порядка

При реорганизации тестов:

1. Сначала классифицировать существующие тесты.
2. Затем определить целевой каталог.
3. Перемещать файлы без изменения тестовой логики, если изменение не требуется отдельно.
4. После перемещения проверить импорты и ссылки на fixtures.
5. Запустить тестовый набор.
6. Проверить, что количество и смысл тестов не изменились.
7. Проверить, что integration/E2E тесты по-прежнему правильно управляют Cleanup.

## 14. Supabase

Реорганизация тестов **не должна сама по себе изменять удалённую Supabase**.

Создание, изменение или удаление схемы, миграций и данных удалённой Supabase выполняется только при отдельном прямом разрешении пользователя.

## 15. Главный принцип

Структура тестов должна отвечать на два вопроса без чтения содержимого файла:

1. **Что проверяется?** — область системы.
2. **На каком уровне проверяется?** — unit, API, contract, integration или E2E.

Если по расположению файла невозможно однозначно определить оба ответа, файл классифицирован неправильно и структуру следует пересмотреть.
